# 스프린트 기록

> 이 프로젝트가 **실제로 어떻게 흘러갔는지** 남기는 기록이다.
> - 무엇을 만들지, 무엇을 정했는지(계획과 결정의 최신 상태) → [`PLANNING.md`](PLANNING.md)
> - 실제로 무엇을 했고, 무엇에 막혔고, 무엇을 바꿨는지(진행 기록과 회고) → **이 파일**
> - 문제 하나하나의 원인과 해결 과정 → [`troubleshooting/`](troubleshooting/)
>
> 스프린트가 끝날 때마다 아래 틀로 한 칸씩 추가한다. 회고(KPT)는 직접 고쳐 쓴다.

## 한 조각을 만드는 흐름

```
1. 정하기   PLANNING 15절의 조각 표에서 다음 조각을 고른다
2. 만들기   DB(엔티티) → 서비스 → 화면(JSP) + 테스트를 한 번에
3. 확인     테스트 통과 → 확인용 DB로 실제 실행 → (필요하면) 휴대폰으로 직접
4. 남기기   커밋(feat / fix / chore) → main에 push → CI ✅ 확인
5. 막히면   로그(traceId)로 원인 찾기 → 고치기 → troubleshooting/에 기록
6. 끝나면   이 파일에 스프린트 기록 + 회고(KPT), PLANNING의 조각 표, 결정 갱신
```

### 바뀐 결정
- 분석 결과 사용자 보정: 처음부터 제외 → 올릴 때 "내가 보고 확정"을 고른 글에 추가 (JM-74)
- 확정 횟수: 여러 번 다시 고칠 수 있음(첫 안) → 글마다 한 번 (나중에 데이터로 쓰기 쉽게)
- 확정할 때의 확인: 항상 글 비밀번호(첫 안) → 방금 올린 브라우저는 비밀번호 없이
- 확정한 뒤의 표시: 확정한 값이 AI의 답을 대체 → AI의 값과 확정한 값을 함께 (AI, REAL)
- 합계 표시: 큰 칼로리 숫자 아래에 탄수화물, 단백질, 지방 → 가로 한 줄에 칼로리, 탄, 단, 지와 꼬리표
- 삭제된 피드백: 목록에서 빠짐 → 줄을 남겨 번호와 안내 글만 보여 줌. 공지와 피드백 목록에 글 번호 (JM-76)
- 운영자 답변: 글마다 한 칸이라 다시 달면 덮어씀 → 달 때마다 한 줄씩 쌓여 순서대로 모두 보임. 예전 답변도 순서대로 되살림 (JM-77)
- 답변 글의 말투: 정해 둔 것이 없어 해요체와 합니다체가 섞임 → 문어체로 쓰고, 한 글의 첫 답변은 "피드백 감사합니다 :)"로 끝냄 (JM-77, 운영자)
- 업로드 한도: IP마다 1분 3번, 하루 30번 → 브라우저마다 1분 5번, 하루 30번 + IP 하루 200번 + 전체 하루 500개 (JM-79, 발표 중 발견)
- 운영자 기능: 화면 없이 API만 → 관리자 화면 더함 (등록한 노트북 브라우저에서만 비밀번호로, JM-82. 휴대폰 인증 앱은 보류). API 열쇠는 그대로 서버에만
- 음식이 아닌 사진: 피드에 그대로 보이고 칼로리 칸만 비움 → 사진을 가리고 운영자가 확인해 올리거나 삭제, 운영자에게 메일 (JM-80, 운영자 결정)
- 운영 통계를 보는 곳: 서버에서 curl로 API만 → 관리자 화면에 "통계" (JM-75)
- 지역 통계: 하지 않음(기획서 4.2절 제외) → 운영자 통계에서만 사진 위치로 행정동까지, IP로 시/도까지 센다. 공개 통계는 그대로 제외 (JM-85, JM-86, 운영자 결정: 사진 위치 + IP 시/도)

### 회고 (KPT, 초안)
- **Keep**: 완료 기준 세 가지를 모두 채웠다 (S5의 Try대로 세 가지로 줄여 잡았다). 고쳐 쓰는 AI는 로컬에서 운영자 검토를 네 번 거쳐 배포했고, 통계로 첫 실제 숫자를 얻었다 (확정률 87.5%, AI 첫 답 그대로 28.6%, 칼로리는 AI가 평균 90kcal 적게 잡음). 11-13 발표에서 드러난 문제(같은 와이파이의 업로드 막힘, 음식이 아닌 사진)는 이틀 안에 고쳤다 (JM-79는 11-14 PR #40, JM-80은 11-15 PR #42). JM-75와 JM-86은 머지 전에 검토 에이전트가 결함을 잡았다 (JM-75의 반올림 규칙, JM-86의 enum 칸과 404로 처음 들어온 방문). 테스트는 154개에서 281개로 늘렸고, 변경 전후 사진과 숫자를 이슈마다 남겼다.
- **Problem**: S5의 Try 가운데 "중간에 들어온 요청은 급한 것이 아니면 다음 스프린트 후보로 쌓는다"는 지키지 못했다. 운영자 요청과 발표 중 발견한 일 8가지가 먼저 끼어들어, 완료 기준인 JM-75 통계는 사용 한도까지 겹쳐 스프린트 마지막 날에야 배포했다. 검토 에이전트를 많이 써서 주간 사용 한도가 다 되어 하루 반 가까이 멈췄다. 쌓아 둔 PR 둘(#45, #46)은 필수 검사가 돌지 않아 닫았다 다시 열어야 했다. 배포 뒤 실제 통계를 서버의 운영자 열쇠로 읽는 것은 Claude Code 자동 모드의 보호 규칙에 막혀, 운영자가 노트북에서 관리자 화면을 열었다 (관리자 비밀번호를 잊어 15분 막히기도 했다).
- **Try**: 다음 스프린트도 "이번에 할 것"은 세 개 안쪽으로 정한다. 끼어드는 요청은 먼저 Jira에 다음 후보로 올리고, 쓰는 사람이 막히는 일(JM-79 같은 것)만 바로 한다. 검토 에이전트는 PR마다 10개 안쪽으로 쓴다. PR은 되도록 쌓지 않고, 쌓아야 하면 머지 순서와 "닫았다 다시 열기"를 PR 본문에 적는다. 배포 뒤 실제 숫자 확인은 처음부터 운영자가 노트북에서 여는 순서로 잡는다.
