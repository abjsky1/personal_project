# 스프린트 기록

> 이 프로젝트가 **실제로 어떻게 흘러갔는지** 남기는 기록이다.
> - 무엇을 만들지, 무엇을 정했는지(계획과 결정의 최신 상태) → [`PLANNING.md`](PLANNING.md)
> - 실제로 무엇을 했고, 무엇에 막혔고, 무엇을 바꿨는지(진행 기록과 회고) → **이 파일**
> - 문제 하나하나의 원인과 해결 과정 → [`troubleshooting/`](troubleshooting/)
>
> 스프린트가 끝날 때마다 아래 틀로 한 칸씩 추가한다. 회고(KPT)는 직접 고쳐 쓴다.

## 한 조각을 만드는 흐름

```
1. 정하기   PLANNING 15절의 조각 표에서 다음 조각을 고른다
2. 만들기   DB(엔티티) → 서비스 → 화면(JSP) + 테스트를 한 번에
3. 확인     테스트 통과 → 확인용 DB로 실제 실행 → (필요하면) 휴대폰으로 직접
4. 남기기   커밋(feat / fix / chore) → main에 push → CI ✅ 확인
5. 막히면   로그(traceId)로 원인 찾기 → 고치기 → troubleshooting/에 기록
6. 끝나면   이 파일에 스프린트 기록 + 회고(KPT), PLANNING의 조각 표·결정 갱신
```

### 만난 문제
- 예외를 모두 500으로 바꾸는 처리만 두면 Spring 기본 예외(404·405)까지 500이 된다 → `ResponseEntityExceptionHandler` 상속으로 해결, 테스트로 고정.
- 혼자 하는 개발에 PR → CI 확인 → 머지 → 정리 과정이 생각보다 오래 걸렸다.

### 바뀐 결정 (S0 끝 무렵)
- Flyway 제거 → JPA `ddl-auto=update` (운영 방식은 S4에서)
- React → JSP (서버 하나로 단순하게)
- 배포 전까지 PR 없이 `main`에 직접 push

### 회고 (KPT · 초안)
- **Keep**: 문제를 볼 장치(traceId, 에러 포맷, CI)를 기능보다 먼저 깔았다.
- **Problem**: 처음에 도구를 많이 넣고 시작했다(Flyway, React, PR 과정). 지금 단계에 비해 무거웠다.
- **Try**: 필요해질 때 넣기. 라이브러리도 기능을 만들 때 한 줄씩 추가한다.

### 바뀐 결정
- 썸네일 400px → 600 × 600 정사각형 (휴대폰 한 줄 한 장에서 선명하게)
- 위치 좌표는 원본 정밀도(소수점 6자리)로 저장, 대신 화면·API·로그 어디에도 내보내지 않음
- 촬영 시각은 위치와 같은 동의를 받았을 때만 저장
- WebP 제외, 이미지 처리 동시 실행 제한은 S4로

### 회고 (KPT · 초안)
- **Keep**: 조각마다 테스트 + 실제 실행으로 확인했다. 로그 한 줄(traceId, 요청 기록, 사진 정보 종류)로 아이폰 문제와 중복 업로드의 원인을 바로 찾았다.
- **Problem**: 휴대폰 테스트를 S1 맨 끝에 한 번에 해서, 중복 업로드 같은 사용성 문제를 늦게 발견했다. 개발 도구 문제(VS Code 빨간 줄, 캐시, 포트)에 시간이 꽤 들었다.
- **Try**: S2부터는 화면이 바뀌는 조각마다 휴대폰으로 한 번씩 눌러 본다. `build.gradle`을 바꾸면 바로 `Java: Reload Projects`.
