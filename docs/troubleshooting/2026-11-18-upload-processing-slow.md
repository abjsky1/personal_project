# 글 올리기의 서버 처리가 p50 1.45초 (사진을 통째로 펼친다)

- **종류**: 찾은 문제 (측정)
- **발견**: 2026-11-18, JM-91 기준선. 2026-11-19 대용량 사진 점검에서 단계별 시간을 쟀다
- **상태**: 진행 중. 아래 2(목표 크기로 읽기)는 JM-94로 했다 (2026-11-20 배포). 운영 p50 1,453 → 1,318 ms (11-18 ~ 11-25, 33건). 1(단계별 기록)은 JM-98, 3은 아직
- **영향**: 사진을 고르고 "올리기"를 누른 뒤 서버에서만 1 ~ 2초, 느리면 4초 넘게 기다린다. 사진은 한 번에 한 장씩 처리하므로 여럿이 동시에 올리면 줄을 선다

## 현상

- CloudWatch 앱 기록 (11-04 ~ 11-19, 올리기 성공 143건): **p50 1,453 ms**, p95 4,540 ms, 최대 5,420 ms. 서버 안의 시간만이다
- nginx가 잰 사람의 올리기 (사진을 받는 시간까지): p50 2,105 ms, p95 7,831 ms. 올리기 시간의 대부분이 서버 처리다
- 로컬에서 운영과 같은 힙(512 MB)으로 지금 코드를 단계별로 쟀다 (11-19, 합성 12MP 세로 사진, 가운데 값): 머리 읽기 1 ms, 위치와 촬영 시각 읽기 0 ms, **펼치고 돌리기 666 ms**, 본 사진 만들기 164 ms, 썸네일 만들기 220 ms. 펼치기가 절반이 넘는다
- 사진 크기별 처리 시간 (같은 조건): 12MP 가로 707 ms, 12MP 세로 1,120 ms, 24MP 가로 1,437 ms, 24MP 세로 2,173 ms
- 원본 크기와 해상도는 어디에도 기록되지 않는다. 실제 사용자 사진이 얼마나 컸는지 지금은 모른다

## 원인

`ImageProcessor.process`가 원본 사진을 원래 크기 그대로 메모리에 펼친 뒤 방향을 돌리고, 그다음에 긴 변 1280과 600으로 줄인다. 휴대폰 사진(1,200만 화소 이상)을 다 펼치는 데 시간과 메모리가 가장 많이 든다. 그 뒤에 S3 저장 두 번(본 사진, 썸네일), 비밀번호 해시(BCrypt), DB 저장이 차례로 이어진다. 처리는 메모리를 지키려고 `synchronized`로 한 장씩 한다.

## 앞으로 해결해 나갈 것

1. 올리기마다 한 줄 기록: 원본 바이트, 가로 세로, 단계별 시간(읽기, 줄이기, S3 저장), 저장 바이트. 실제 원본 크기와 줄어든 비율을 쌓는다
2. 원본을 다 펼치지 않고 목표 크기로 읽는다. 로컬 시험(11-19, 코드에는 아직 넣지 않음): 긴 변 2560으로 읽으면 12MP 세로 1,120 ms → 670 ms (필요한 힙 256 MB → 128 MB), 24MP 세로 2,173 ms → 1,400 ms. 띄엄띄엄 읽는 방법은 더 빠르지만(24MP 세로 775 ms) 잔무늬가 생길 수 있어 실제 사진으로 눈으로 비교한다
   - → 긴 변 2560으로 읽기로 했다 (JM-94, PR #51). 같은 도구로 번갈아 잰 처리 시간: 12MP 세로 832 → 538 ms, 24MP 세로 1,350 → 871 ms. 운영 올리기 p50 1,453 → 1,318 ms, JM-105 배포 뒤만 1,183 ms (11건). [큰 사진 메모리 부족](2026-11-19-large-photo-oom.md)도 같이 막았다
3. S3 저장 두 번을 함께 보내거나, 브라우저에서 미리 줄여 보내는 방법(올리는 시간과 데이터도 준다)을 숫자를 보고 정한다
4. 목표: 서버 처리 p50 1.45초 → 0.8초 아래 (바꾼 뒤 같은 방법으로 잰다)
