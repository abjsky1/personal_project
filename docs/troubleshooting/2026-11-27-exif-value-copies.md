# 촬영 정보(EXIF) 칸이 같은 값을 겹쳐 가리키는 작은 사진 한 장으로 메모리가 모자랐다

- **종류**: 찾은 문제 (소스 분석). 메모리 약점이라, 고칠 때까지 비공개 기록 저장소에 두었다가 2026-11-27 공개
- **발견**: 2026-11-27. JM-108 PR 전 검토에서 "따로 살펴볼 후보"로 나온 것을 사진 정보 라이브러리(metadata-extractor 2.21.0) 소스로 따라가 셈했고, 운영자 OK 뒤 로컬에서 재현했다. 위치와 촬영 시각을 읽기 시작한 때부터 있던 것이다
- **상태**: 해결 (JM-111 PR #69, 2026-11-27 배포, 같은 날 운영 확인)
- **영향** (고치기 전): 로그인 없이 누구나 올릴 수 있는 작은 사진 한 장(EXIF 약 12 KB)으로 앱 힙(512 MB)이 모자라, 올리기가 500이 되고 에러 경보가 울릴 수 있었다. 힙이 차는 동안 다른 요청이 멈추고, 같은 때 들어온 다른 요청도 메모리가 모자랄 수 있었다
  - EXIF가 약 6 KB면 메모리 부족까지는 가지 않아도 힙을 꽉 채워 1.2초가 걸리고, 그동안 다른 요청이 0.3초쯤 멈췄다. 에러가 나지 않아 보이지 않는다
  - JPEG와 PNG가 같다. 화소 수, 펼친 크기 한도(JM-94, JM-105)와 PNG 조각 버리기(JM-108)는 그림 크기와 쓰지 않는 조각만 보므로 지나갔다
  - 운영에서 이 일로 보이는 실패는 없었다 (11-04 ~ 11-25 올리기 5xx 0건, [prevent-photo-upload](prevent-photo-upload.md) 3번)

## 현상 (로컬, 힙 512 MB, SerialGC)

- EXIF는 TIFF 형식이라, 목록(IFD)의 칸마다 값이 있는 자리를 적는다. 사진 정보 라이브러리는 칸마다 그 자리의 값을 새로 베끼고, 하위 목록을 가리키는 칸이면 값마다 디렉터리를 하나씩 새로 만들었다. 여러 칸이 같은 자리를 겹쳐 가리키는지, 베낀 값의 합이 얼마인지는 보지 않았다
- 그래서 작은 EXIF가 힙에서 크게 불었다: 하위 목록 칸은 값 1바이트에 약 45바이트(빈 디렉터리), 분수(RATIONAL) 칸은 약 4.5바이트. JPEG의 EXIF 조각 하나(64 KB)를 겹치는 칸으로 채우면 셈으로 약 15 GiB와 1.5 GiB다. 셈한 객체 크기는 재어 보니 맞았다 (빈 디렉터리 180 B, 분수 하나 35 B)
- 100 x 100 그림에 EXIF 덩어리 하나를 넣은 시험 파일을, old를 약 26 MiB(빈 힙에 가까움)와 약 190 MiB(11-20에 운영에서 읽은 old 사용량)로 채운 힙에서 처리했다
  - 하위 목록 11.7 KB(파일 13 KB)와 분수 37.0 KB(파일 39 KB)부터 JPEG와 PNG, 두 old 모두 OutOfMemoryError
  - 메모리가 모자라기 전 3.7 ~ 17.4초 동안 전체 GC가 12 ~ 37번 돌았다 (걸린 시간의 91 ~ 97%). 그동안 다른 요청이 멈췄다 (한 번에 가장 길게 1.4초)
  - 옆 스레드(다른 요청 흉내)도 OutOfMemoryError를 받았다: 힙을 채운 16번 가운데 15번
  - 사진 정보 로그 한 줄이 1,149만 자까지 커졌다 (빈 디렉터리 이름이 줄줄이 들어감)
- 같은 읽기 안의 XMP 확장 조각: 조각에 적힌 전체 길이로 배열을 한 번에 만들어, 1.6 KB JPEG 하나가 약 2 GiB를 달라고 해 OutOfMemoryError, 길이가 0x80000000 이상이면 NegativeArraySizeException
- 실제 앱(로컬 war, 힙 512 MB, 같은 때 피드를 0.2초마다): 13 KB JPEG가 25.4초 만에 500, 그동안 피드 요청 하나가 18.5초를 기다렸다. 13 KB PNG는 36.9초 만에 500. ERROR "Unhandled exception" 5줄(경보가 울리는 줄)과, 표준 오류로만 나가 경보에 걸리지 않는 Tomcat 도우미 스레드의 종료 1줄. 끝난 뒤 메모리는 돌아왔고 앱은 계속 응답했다

## 원인

- `ImageProcessor.readMetadata`가 사진 정보를 라이브러리의 통째 읽기(`ImageMetadataReader.readMetadata`)로 읽었다. 이 앱이 쓰는 값은 GPS의 위치와 EXIF의 촬영 시각뿐인데, 통째 읽기는 정보 13가지(XMP, ICC, 제조사 칸, 미리보기 그림 등)를 모두 돌고 칸마다 값을 베꼈다
- 라이브러리의 TIFF 읽기는 칸의 값이 데이터 안에 있는지만 본다. 칸 수는 목록 하나에 65,535까지이고, EXIF 덩어리 수에도 한도가 없다 (JPEG는 조각마다, PNG는 eXIf 조각마다 따로 읽는다)
- 하위 목록 칸(SubIFDs)은 값마다 새 디렉터리를 먼저 만들고, 가리킨 자리를 이미 읽었는지는 그 뒤에 본다. 그래서 같은 자리를 겹쳐 가리켜도 빈 디렉터리가 계속 남는다
- 메모리 부족과 라이브러리 안의 RuntimeException은 잡지 않아 500과 ERROR가 됐다

## 해결 (JM-111, PR #69)

1. 새 클래스 `PhotoMetadataReader`: JPEG는 그림 데이터 앞의 첫 "Exif" 조각, PNG는 첫 eXIf 조각(65,527 B까지, JPEG의 EXIF 조각 하나와 같은 크기)만 꺼내 라이브러리의 TIFF 읽기를 직접 부른다. 라이브러리의 손잡이(`ExifTiffHandler`)를 이어받은 손잡이가
   - 첫 목록(IFD0)에서 EXIF 목록과 GPS 목록으로 한 번씩만 들어간다. 그 밖의 하위 목록과 다음 목록(썸네일)은 들어가지 않는다 → 디렉터리는 많아야 셋
   - 쓰는 칸 일곱 개(촬영 시각, 초 아래 자리, 시간대, GPS의 북위/남위, 위도, 동경/서경, 경도)와 로그 이름을 가리는 데 쓰는 제조사 이름만, 값 64바이트까지 베낀다. 나머지 칸, 제조사 칸, XMP, ICC, 미리보기 그림은 읽지 않는다
   - 하위 목록 자리 값을 1만 개 넘게 보면 깨진 EXIF로 보고 멈춘다 (보통 사진은 스무 개도 안 된다)
2. 위치와 시각 계산은 그대로 라이브러리 (`GpsDirectory.getGeoLocation`, `ExifSubIFDDirectory.getDateOriginal`) → 보통 사진은 값이 전과 같다
3. 생각하지 못한 RuntimeException이 나도 글은 정보 없이 올라가고, WARN 한 줄에 스택을 남긴다. 메모리 부족 같은 Error는 감추지 않는다
4. `Photo metadata` 로그: 사진 안의 정보 덩어리 이름을 차례대로 12가지까지 남긴다. 이름은 전의 디렉터리 이름에 맞춰, [아이폰 사진의 위치](2026-10-30-iphone-gps-missing.md)에서 쓰는 지표(보관함 사진과 바로 찍은 사진 가르기)가 이어진다
5. 견준 다른 후보: 위치와 시각 칸을 직접 읽고 라이브러리를 빼기(코드와 시험이 가장 많고, 라이브러리가 받아 주던 조금 틀린 EXIF의 위치를 놓칠 수 있다), 지금 읽기는 두고 앞에서 EXIF를 훑어 겹침을 걸러 내기(라이브러리가 따라가는 길을 똑같이 따라가야 해서 하나라도 빠뜨리면 구멍이 남는다). 운영자가 필요한 칸만 읽는 안을 골랐다 (11-27)
6. 하지 않은 것: 메모리 부족을 잡아 정보 없이 올리기(500만 감추고 다른 요청이 멈추는 일은 그대로), 메모리 부족이면 JVM 끄기(사진 한 장으로 앱이 다시 켜져 더 나쁘다)

## 전후

로컬, 힙 512 MB, SerialGC, old 약 26 MiB와 약 190 MiB. 같은 시험 파일 25개 x 두 old (50번). 고치기 전은 main `29c16cd`

| | 고치기 전 | 고친 뒤 |
|---|---|---|
| OutOfMemoryError (50번 가운데) | 20번 (그 밖에 NegativeArraySizeException 2번) | **0번** (모두 219 ~ 417 ms에 처리) |
| 한 판의 전체 GC가 가장 많을 때 | 37번, 16.5초 | 0번 |
| 다른 요청이 멈춘 가장 긴 시간 | 1,447 ms | 7 ms |
| 옆 스레드가 받은 OutOfMemoryError (합) | 60번 | 0번 |
| 사진 정보 로그 한 줄이 가장 길 때 | 11,492,180자 | 150자 |
| 보통 사진의 위치와 시각 | | 같음 (사진 12가지로 통째 읽기와 견줌) |
| 보통 사진 처리 시간 | 307 ~ 341 ms | 251 ~ 268 ms (실행마다의 흔들림 안) |
| 실제 앱: 13 KB JPEG | 500, 25.4초 (그동안 피드 18.5초) | 302, 0.19초 (피드 0.054초) |
| 실제 앱: 13 KB PNG | 500, 36.9초 | 302, 0.16초 |
| 실제 앱: XMP 확장 둘 | 500 (0.30초, 0.05초) | 302 |
| 실제 앱의 ERROR 줄 | 5줄 | 0줄 |
| 운영 (11-27 18:04, 운영자의 아이폰 사진 세 장, 위치 동의) | | 셋 다 302, 위치와 시각을 읽음, 머지 뒤 ERROR와 WARN 0줄 |

- 고친 뒤 남는 메모리: 모든 시험 파일이 디렉터리 3개 이하, 칸 5개 이하라 재는 틀의 흔들림(약 2.6 MiB)보다 작았다. 읽는 시간은 0.04 ~ 1.4 ms
- 운영의 새 로그 줄 예: `Photo metadata: directories=[JPEG, JFIF, Exif IFD0, Exif SubIFD, GPS, Apple Makernote, Exif Thumbnail, MPF, ICC Profile, APP10], gps=true, takenAt=true` (읽지 않는 덩어리는 이름만)
- 전과 다른 드문 경우: 첫 EXIF 덩어리만 읽는다, Photoshop 조각 안의 EXIF는 읽지 않는다, 64바이트가 넘는 값과 64 KB가 넘는 PNG eXIf는 읽지 않는다 (그런 사진은 위치와 시각 없이 올라간다)

## 재발 방지

- 테스트 21개를 더했다 (전체 465개)
  - `PhotoMetadataReaderTest` 19개: 통째 읽기와 위치, 시각이 같은지 사진 12가지로 견준다 (바이트 순서 MM과 II, 남위와 서경, PNG, 초 아래 자리와 시간대, JFIF 뒤의 EXIF, 채움 바이트, IDAT 뒤의 eXIf 등). 하위 목록 칸이 아주 많은 EXIF와 큰 eXIf, 64바이트가 넘는 값은 읽지 않는다
  - `ImageProcessorTest` 2개
- PR 전 검토 (에이전트 하나): 처음 고친 판에서 PNG eXIf가 크면 읽는 시간이 크기의 제곱으로 느는 것(1 MB에 2.0초, 메모리는 그대로)을 찾아 eXIf 크기 상한과 하위 목록 자리 값 상한을 넣었다. 로그 이름을 운영 지표에 맞췄고, 생각하지 못한 예외의 스택을 남기게 했다
- 운영 로그의 `Photo metadata` 줄로 실제로 올라오는 사진의 정보 덩어리를 본다
- [prevent-photo-upload](prevent-photo-upload.md) 3번에 더했다

## 배운 것

- 라이브러리의 "사진 정보 읽기" 한 줄 뒤에서 무엇을 얼마나 베끼는지는 소스로 봐야 안다. 쓰는 값은 둘인데 읽기는 열세 가지를 돌았다
- 읽는 범위를 쓰는 값에 맞게 좁히는 것(허용 목록)이 나쁜 입력을 하나씩 막는 것(차단 목록)보다 짧고 확실했다. 메모리가 새는 길(하위 목록, 값 베끼기, XMP 확장)이 셋이었는데 한 번에 닫혔다
- 메모리 약점은 에러가 나지 않을 때도 비싸다. 메모리 부족 아래의 크기도 모든 요청을 멈췄고, 숫자로 재어야 보였다
