# 미리 막은 문제: 보안과 개인정보

- **종류**: 미리 막은 문제 (예방). 문제가 되기 전에 예상해서 만들어 둔 장치와, 그것이 실제로 어떻게 확인됐는지
- **정리**: 2026-11-19. 시점은 각 장치를 처음 넣은 커밋
- 사진 저장소의 보안은 [prevent-photo-upload](prevent-photo-upload.md)의 5 ~ 7에 있다. 2026-11-19 점검에서 찾은 보안 약점은 고친 뒤에 이 폴더에 전후로 적는다 (고치기 전에는 비공개 기록에만 둔다)

## 1. DB가 새면 비밀번호까지 새는 문제 → BCrypt로만 저장

- **예상한 문제**: 회원 가입 없이 글, 댓글, 피드백마다 비밀번호를 받는다. 그대로 저장하면 DB가 샐 때 비밀번호가 그대로 보이고, 다른 사이트에 같은 비밀번호를 쓰는 사람이 피해를 본다
- **미리 한 것**: 비밀번호는 BCrypt로 바꿔서만 저장한다 (한 방향, 소금이 섞여 같은 비밀번호도 매번 다른 값). 로그인 기능 전체(Spring Security)는 넣지 않고 암호 도구만 쓴다. 비밀번호가 틀려도 로그에는 글 번호만 남기고 입력값은 남기지 않는다
- **언제**: 2026-10-29 S1-1 (`88f7306`)

## 2. 세션 쿠키를 가로채거나 빌려 쓰는 문제 → https 전용, 다른 사이트 form 차단

- **예상한 문제**: 세션 쿠키가 http로 오가면 같은 와이파이에서 엿볼 수 있다. "방금 올린 브라우저는 비밀번호 없이 확정"(JM-74)을 만들면서, 다른 사이트에 숨긴 form이 그 권한을 빌려 확정을 보낼 수 있게 됐다
- **미리 한 것**: 세션 쿠키에 Secure를 붙여 https로만 보낸다. SameSite=lax로 다른 사이트에서 보낸 form에는 쿠키를 싣지 않는다 (링크를 눌러 들어오는 것은 그대로 된다)
- **언제**: Secure 2026-11-03 S4-4 (`ea6ff7c`), SameSite 11-12 JM-74 (`ccc7109`)

## 3. 통신을 엿보거나 바꿔치기하는 문제 → HTTPS, HSTS, 오래된 TLS 끄기, 버전 숨기기

- **예상한 문제**: http는 중간에서 내용을 보거나 바꿀 수 있다. 오래된 TLS(1.0, 1.1)에는 알려진 약점이 있다. 에러 화면에 nginx 버전이 보이면 그 버전의 약점을 노린다
- **미리 한 것**: http 요청은 모두 https로 301 이동, TLS 1.2와 1.3만 받는다. HSTS로 한 번 들어온 브라우저는 6개월 동안 스스로 https로 간다. `server_tokens off`로 버전을 숨긴다. 서비스 인증서는 가비아 Sectigo(JM-67), Let's Encrypt는 예비로 계속 갱신한다
- **언제**: 버전 숨기기 2026-10-31 (`04894e8`), HTTPS와 HSTS 11-03 S4-4 (`ea6ff7c`), 유료 인증서 11-11 (PR #29)

## 4. 가짜 IP로 횟수 제한을 피하는 문제 → nginx가 본 주소로 덮어쓰기

- **예상한 문제**: 횟수 제한은 IP를 쓴다. 사용자가 `X-Forwarded-For` 머리말에 아무 IP나 적어 보내면 제한을 피할 수 있다. 반대로 nginx 뒤에서는 모든 요청이 nginx 주소 하나로 보여 한 사람이 막히면 모두가 막힌다
- **미리 한 것**: nginx가 사용자가 보낸 값을 버리고 직접 본 주소로 덮어쓴다 (`proxy_set_header X-Forwarded-For $remote_addr`). Spring은 내부망(Docker)에서 온 머리말만 믿는다 (`server.forward-headers-strategy=native`)
- **언제**: 2026-10-31 배포 구성 (`04894e8`)

## 5. 접속 기록에 개인정보(IP)가 쌓이는 문제 → IP 없는 기록, 해시, 보관 기간

- **예상한 문제**: nginx 기본 기록은 모든 요청의 IP를 남긴다. 처리방침에는 "접속 IP는 서버 메모리에만 최대 1일"이라고 적었다
- **미리 한 것**: nginx 기록 형식에서 IP와 referer를 뺐다 (`log_format noip`). 횟수 제한에 걸린 IP는 앱이 해시로만 로그에 남긴다. app 로그(CloudWatch)는 90일만 보관한다 (처리방침의 이용 기록 3개월). 방문 지역 통계(JM-86)는 IP를 저장하지 않고 시/도의 하루 합계만 남긴다
- **언제**: IP 없는 기록 2026-11-04 S4-6 (`d5a7451`), 방문 지역 11-18 (PR #46)
- **확인**: 처음 두 번의 배포에서는 설정이 실제로 적용되지 않아 IP가 계속 찍혔다. 이를 찾아 고쳤다 ([2026-11-04-nginx-bind-mount-stale](2026-11-04-nginx-bind-mount-stale.md))
- **남은 것**: IP를 쓰지 않으므로 방문자 수(사람 수)는 셀 수 없다. 대신 방문 수(세션의 첫 화면)를 센다

## 6. 비밀값이 코드와 함께 새는 문제 → 저장소 밖의 .env, 역할, OIDC

- **예상한 문제**: DB 비밀번호, AI 열쇠, AWS 열쇠를 코드나 설정 파일에 적으면 공개 저장소로 함께 나간다
- **미리 한 것**: 비밀값은 서버의 `deploy/.env`(Git에 없음)에만 둔다. S3는 EC2 역할로 접근해 열쇠가 없다. GitHub Actions 배포도 열쇠를 저장하지 않고 OIDC로 그때그때 임시 권한을 받는다 (SSM으로 명령을 보내 서버의 SSH도 GitHub에 열지 않는다). 테스트는 실제 AI를 부르지 않게 열쇠를 비운다
- **언제**: `.env`와 역할 2026-10-31 ~ 11-03 (S4), OIDC 배포 11-04 S4-5 (`781e852`)

## 7. 운영자 기능을 남이 쓰는 문제 → 서버 안에서만 읽는 열쇠, 등록한 기기 하나

- **예상한 문제**: 글을 지우거나 통계를 보는 운영자 기능을 남이 쓰면 안 된다. 열쇠를 PC나 메신저에 복사하면 새기 쉽다
- **미리 한 것**: 운영자 API는 서버 `.env`의 열쇠로만 열리고, 서버에 SSH로 들어가 그 자리에서 읽어 쓴다 (복사하지 않는다). 틀린 열쇠는 로그에 남는다. 관리자 화면(JM-82)은 처음 등록한 노트북 브라우저 하나에서만 비밀번호 칸이 열리고, 운영자 API 열쇠와 따로 둔다
- **언제**: 운영자 API 2026-11-05 S3-3 (`8c57c50`), 관리자 화면 11-14 JM-82 (`79e8db6`)

## 8. 남의 글을 고치거나 지우는 문제 → 비밀번호, 또는 방금 올린 브라우저

- **예상한 문제**: 회원이 없으므로 누가 글의 주인인지 알기 어렵다
- **미리 한 것**: 메모 수정, 글과 댓글 삭제는 그 글의 비밀번호가 맞아야 한다. AI 분석 확정(JM-74)은 방금 올린 브라우저(세션에 글 번호를 기억)면 비밀번호 없이, 아니면 비밀번호로 한다. 지우기는 행을 없애지 않고 상태만 바꾼다 (기획서 5.1절)
- **언제**: 비밀번호 확인 2026-10-29 S1-2 (`0b73c3f`), 방금 올린 브라우저 11-12 JM-74 (`ccc7109`)

## 9. 조회수와 좋아요를 부풀리는 문제 → bot 거르기와 글마다 상한

- **예상한 문제**: 검색 로봇, 링크 미리보기, 스크립트가 조회수와 방문 수를 부풀린다. 좋아요를 스크립트로 계속 누를 수 있다
- **미리 한 것**: User-Agent로 사람이 아닌 요청을 거른다 (`Visitors`, 서버 로그로 트래픽을 셀 때와 같은 낱말 목록). 좋아요는 글 하나에 1분 30번, 하루 300번까지 (IP는 쓰지 않는다)
- **언제**: 2026-11-11 JM-59, JM-72 (`53e284e`), 낱말 목록 확장 11-18 JM-86
- **확인**: 처음에는 좋아요 제한을 IP로 만들었다가, 처리방침에 IP 이용 목적을 "업로드 횟수 제한"으로만 적은 것을 보고 글마다 세는 방식으로 바꿨다 (SPRINTS S5 만난 문제)

## 10. 사진 위치로 사는 곳이 드러나는 문제 → 동의, EXIF 지우기, 합계만

- **예상한 문제**: 사진 위치를 모으면 친구들이 사는 곳이나 일하는 곳이 드러날 수 있다
- **미리 한 것**: 위치는 올릴 때 동의한 경우에만 저장하고, 사진 파일에서는 지운다. 통계는 시/도, 시/군/구, 행정동별 글 수만 보이고 좌표는 내보내지 않는다 (JM-85). 공개 문서(SPRINTS)에는 시/도 숫자만 적는다
- **언제**: 2026-10-30 S1-4 (`3ec563b`), 지역 통계 11-17 JM-85

## 11. 화면 이동을 남기다가 한 사람의 행동 기록이 되는 문제 → 방문 단위, 무작위 번호, 줄인 값

- **예상한 문제**: 사용자 흐름(JM-92)을 남기면 사람마다 본 화면이 쌓인다. IP, 세션 번호, User-Agent 전체, 주소 전체를 함께 두면 같은 사람의 방문을 이어 붙이거나, DB가 샐 때 남의 세션을 빌려 쓰거나, 검색어 같은 값이 그대로 들어간다. 글을 올린 방문이 그 글의 번호를 남기면 흐름이 글쓴이와 이어진다. 지우지 않고 모두 보관하기로 해서(운영자 결정 11-20) 오래 쌓일수록 더 커진다
- **미리 한 것**: 방문 하나 안에서만 잇는다: 이미 쓰는 세션(30분이면 끝남)에 무작위 번호를 붙이고, 쿠키를 새로 만들지 않는다. 표에 IP, 세션 번호, User-Agent 전체, 주소 전체의 칸을 두지 않았다. 들어온 곳은 만들 때 줄인다 (`VisitEntry`): 다른 사이트는 도메인만(IP 주소와 localhost 같은 이름은 버림), utm은 글자, 숫자, 빈칸, `._~+-`만 50자까지(HTML이나 수식, 보이지 않는 글자를 지움), 링크 표시(`fbclid` 등)는 이름만. 이 방문이 올리거나 쓰거나 고친 글(새 글, 피드백, 댓글을 단 글, 확정이나 메모를 고친 글)은 POST가 넘어가는 주소로 기억해 두고 그 방문의 줄에 번호를 남기지 않는다. bot과 관리자로 들어온 적이 있는 세션(로그아웃한 뒤에도)은 뺀다
- **언제**: 2026-11-20 JM-92 (PR #54)
- **확인**: PR 전 검토(에이전트 네 개가 따로 보고 하나가 반박 확인)에서 두 가지를 찾아 고쳤다. ① 글을 올리면 넘어가는 새 글 화면이 그 글의 번호를 남겨 "올린 글의 번호는 남기지 않는다"가 지켜지지 않았다 (처음 테스트가 오히려 그 값을 확인하고 있었다). ② 관리자 화면만 쓰고 로그아웃한 뒤 같은 브라우저로 본 화면은 다시 남았다. 지금은 테스트가 표의 칸 목록을 하나하나 맞춰 보고(둘 칸이 없다), 검색어와 `fbclid`의 값이 어느 칸에도 남지 않는지, 올리기와 댓글과 피드백 뒤의 화면에 번호가 없는지, 실제 로그인과 로그아웃 뒤의 화면이 빠지는지 본다 (`PageFlowInterceptorTest`, `PageFlowTest`, `AdminPageTest`, `PageFlowValuesTest`)
- **남은 것**: 줄의 시각으로 글이나 댓글의 작성 시각과 맞춰 보면 지금 규모에서는 누가 쓴 방문인지 짐작할 수 있다. 화면 사이의 시간을 보려고 시각은 그대로 두고, 흐름 기록을 글쓴이를 찾는 데 쓰지 않는 것을 운영 규칙으로 했다 ([user-flow.md](../user-flow.md) 2절). nginx 접속 기록(IP 없음)에는 주소 전체와 User-Agent 전체가 30MB만큼(2주쯤) 돌며 남는다. 같은 사람의 다른 방문은 일부러 잇지 않는다 (사람 수는 모른다). 운영자가 관리자 로그인 없이 휴대폰으로 본 화면은 섞인다

## 12. 검색어가 화면을 깨거나 기록에 쌓이는 문제 → 글자로만 출력, 그 글자 그대로 찾기, 흐름 기록에는 쪽 번호만

- **예상한 문제**: 검색어(JM-52)는 누구나 넣는 값이다. ① 페이지 제목, 입력칸, 결과 줄, 쪽 번호 링크에 그대로 넣으면 스크립트가 실행될 수 있다(XSS) ② SQL에 이어 붙이면 SQL 주입이 되고, LIKE의 `%`와 `_`를 그대로 넘기면 `%` 한 글자로 모든 글이 나온다 ③ 사용자 흐름(JM-92)에 검색어를 남기면 방문마다 무엇을 찾았는지가 쌓인다 ④ 검색어마다 다른 주소가 생겨 검색 엔진이 끝없이 담아 갈 수 있다
- **미리 한 것**: ① 화면에는 `c:out`으로만 내고, 쪽 번호 링크에는 `URLEncoder`로 바꾼 값을 쓴다 ② 검색어는 SQL 매개변수로만 넘기고, `%`, `_`와 escape 글자 `!`는 앞에 `!`를 붙여 그 글자 그대로 찾는다 ③ 흐름 기록의 검색 결과 줄(`SEARCH`)에는 쪽 번호만 남기고 검색어는 남기지 않는다. 앱의 요청 기록 줄도 경로만 남긴다 ④ 검색 결과 화면에 `noindex`
- **언제**: 2026-11-23 JM-52 (PR #58)
- **확인**: 헤드리스 Chrome으로 `<script>alert(1)</script>`를 찾아 글자로만 보이고 script 태그는 페이지 자체의 것뿐인 것을 봤다 (기록 저장소 `update_picture/JM-52`). `a_b`, `c%d`, `e!f`가 그 글자 그대로만 맞는 테스트, 흐름 기록에 `SEARCH`와 쪽 번호만 남는 테스트(`PageFlowInterceptorTest`). PR 전 검토(에이전트 둘)도 제목, 입력칸, 결과 줄, 쪽 번호 링크에 `"><script>…'&#`를 넣어 모두 글자로만 나오는 것과, 앱 로그, 에러 화면, 흐름 기록 어디에도 검색어가 남지 않는 것을 확인했다. 검토에서 찾은 NBSP 하나만 보내면 빈칸이 든 이름이 모두 나오던 것은 고쳤다 ([찾은 문제](2026-11-23-search-gaps-before-merge.md) ⑩)
- **남은 것**: nginx 접속 기록에는 다른 주소와 같이 검색어가 들어간 주소가 남는다 (IP는 없음, 서버 파일 10 MB 세 개를 돌려 씀)
