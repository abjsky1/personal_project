# 2026-10-30 · 올리기 버튼을 여러 번 눌러 같은 글이 9개 올라감

| 항목 | 내용 |
|---|---|
| 발견 | S1 휴대폰 실기기 테스트 (아이폰 Safari, 핫스팟) |
| 심각도 | 중간 — 데이터가 잘못 쌓임, 배포 후 S2에서는 AI 분석 한도도 같이 소모됨 |
| 상태 | 해결 (`fix` 커밋) |

## 현상
- 올리기 버튼을 누른 뒤 화면이 몇 초 동안 그대로 멈춘 것처럼 보였다 ("버퍼").
- 반응이 없는 줄 알고 버튼을 연속으로 눌렀더니 **같은 사진의 글이 9개(41~49번)** 생겼다.

## 영향
- 같은 글이 여러 개 쌓인다. 사용자가 하나씩 지워야 한다.
- S2부터는 글마다 AI 분석이 돌기 때문에, 무료 LLM 일일 한도를 중복 글이 갉아먹게 된다.

## 원인 찾기
서버 로그(`TraceIdFilter`의 요청 기록 한 줄)로 확인했다.

```
16:06:00.802  [71e84df5] POST /posts -> 302 (1120ms)
16:06:01.842  [7cbc3be2] POST /posts -> 302 (1243ms)
...
16:06:05.239  [90698d4d] POST /posts -> 302 (2181ms)
```

- **5초 동안 `POST /posts`가 9번** 들어왔고, traceId가 모두 달랐다 → 서로 다른 9개의 요청.
- 요청 하나에 1.1~2.4초가 걸렸다. 핫스팟으로 원본 사진(수 MB)을 보내고, 서버에서 사진을 처리하는 시간이다.
- 화면에는 그동안 아무 변화가 없어서, 사용자는 눌린 줄 몰랐다.
- 서버 쪽 동작은 정상이었다. 요청이 9번 오면 9번 저장한 것뿐이다.

## 해결
화면(JSP)에서 처음 누를 때 버튼을 막는다.

- `new.jsp`: 제출하는 순간 버튼을 `disabled`로 바꾸고 글자를 **"올리는 중…"**으로 바꾼다.
- `detail.jsp`: 삭제 버튼도 같은 방식으로 막는다. 연속으로 누르면 두 번째 요청은 이미 지워진 글이라 404 에러 화면이 나오기 때문이다.
- 아이폰 Safari는 "뒤로 가기"를 하면 이전 화면을 그대로 되살린다(bfcache). 그러면 버튼이 막힌 채 남으므로, `pageshow` 이벤트에서 버튼을 원래대로 돌린다.

## 확인
- 브라우저에서 실제 사진을 넣고 버튼을 **3번 연속** 눌렀다 → 글 **1개**, 서버 요청 **1번**.
- 삭제 버튼을 3번 연속 눌렀다 → 삭제 요청 **1번**, 에러 화면 없이 목록으로 이동.

## 재발 방지 · 남은 것
- 시간이 걸리는 form(사진 업로드, 앞으로의 댓글·피드백 작성)은 **누르면 바로 막고 진행 중 표시**를 기본으로 한다.
- 이 방법은 화면에서만 막는다. 네트워크가 끊겨 브라우저가 다시 보내는 경우까지 막으려면 서버에서도 막아야 한다(요청마다 1회용 번호를 붙이는 방식 등). 지금은 과하다고 보고, 배포 후 중복 글이 로그에 보이면 추가한다.

## 배운 점
- 기능이 "동작"하는 것과 사용자가 "쓸 수 있는" 것은 다르다. 테스트 코드로는 버튼을 한 번만 누르니 이 문제가 드러나지 않았고, 실제 휴대폰에서 사람이 써 보고서야 나왔다.
- 요청마다 남기는 로그 한 줄(메서드, 경로, 상태, 걸린 시간 + traceId) 덕분에 "몇 번, 얼마 간격으로, 얼마나 걸렸는지"를 바로 확인할 수 있었다.
