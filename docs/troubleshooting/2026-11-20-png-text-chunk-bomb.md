# 글자 조각이 아주 많은 작은 PNG 한 장으로 메모리가 모자랐다

- **종류**: 찾은 문제 (PR 전 검토). 메모리 약점이라, 고칠 때까지 비공개 기록 저장소에 두었다가 2026-11-27 공개
- **발견**: 2026-11-20, JM-105 PR 전 검토. 검토 에이전트가 자바 소스에서 찾았고, 로컬에서 재현했다. JM-105가 만든 것이 아니라 전부터 있던 것이다
- **상태**: 해결 (JM-108 PR #66, 2026-11-27 배포)
- **영향** (고치기 전): 그림은 100 x 100이고 파일은 1 MB도 안 되는 PNG 한 장으로 앱 힙(512 MB)이 모자라, 올리기가 500이 되고 에러 경보가 울릴 수 있었다. 같은 때 들어온 다른 요청도 메모리가 모자랄 수 있었다
  - 사진 처리는 한 장씩이라 여러 장을 보내면 줄을 서지만, 한 장마다 같은 일이 일어난다
  - 운영에서 이 일로 보이는 실패는 없었다 (11-04 ~ 11-25 올리기 5xx 0건, [prevent-photo-upload](prevent-photo-upload.md) 3번)

## 현상 (로컬, 힙 512 MB, SerialGC)

- PNG에는 그림 말고도 글자를 담는 조각(tEXt, zTXt, iTXt)이 있고, zTXt와 iTXt는 압축할 수 있다. 파일에서는 작은 조각이 펼치면 수백 KB가 된다
- 압축한 글자 조각을 많이 넣은 PNG(700 KB)는, 운영처럼 old를 채우지 않은 빈 힙(old 26 MiB)에서도 OutOfMemoryError로 실패했다. 머리 검사에서 자바의 PNG 읽기가 조각을 풀다가 모자랐다
- 2026-11-26에는 큰 조각 하나만 넣은 PNG(306 KB, zTXt나 압축한 iTXt)로도 같은 일이 일어나는 것을 찾았다. 이때는 머리 검사를 지나, 위치와 촬영 시각 읽기(metadata-extractor)에서 모자랐다
- 그림은 화소 수도 펼친 크기도 아주 작아서, 화소 한도와 펼친 크기 한도(JM-94, JM-105)에 걸리지 않았다

## 원인

- 자바의 PNG 읽기(`PNGImageReader`)는 사진 정보를 읽을 때 zTXt, iTXt 조각을 하나에 256 KB까지 풀어 모두 쥔다. 조각 수에는 한도가 없다
- 이 앱에서 PNG를 읽는 곳 셋이 모두 이 조각을 읽었다
  - 머리 검사(JM-105, `getImageTypes`): 회색, RGB, 팔레트 PNG에서 사진 정보를 읽는다
  - 위치와 촬영 시각 읽기(metadata-extractor): 이 조각을 크기 한도 없이 푼다. 그래서 조각 하나로도 모자랐다
  - 펼치기(Thumbnailator): 방향을 보려고 사진 정보를 건너뛰지 않고 읽는다
- 화소 한도와 펼친 크기 한도는 그림의 크기만 보므로, 그림 밖의 데이터는 막지 못했다

## 해결 (JM-108, PR #66)

1. PNG면 머리 검사보다 먼저, 그림을 펼치는 데 필요한 조각(IHDR, PLTE, tRNS, IDAT)과 촬영 정보 조각(eXIf), 끝 표시(IEND)만 남기고 나머지 조각과 IEND 뒤의 바이트는 버린다 (`PngChunks.keepNeeded`). 그 뒤 단계(머리 검사, 위치와 촬영 시각 읽기, 펼치기)는 모두 남긴 파일을 쓴다
   - 조각마다 길이와 종류 8바이트만 보고 건너뛴다. 압축은 풀지 않는다
   - 버릴 조각이 없으면 받은 배열을 그대로 쓴다 (베끼지 않는다). 있으면 맞는 크기로 한 번 베끼고, 버린 조각의 수와 종류, 바이트를 INFO 한 줄(`PNG chunks dropped`)로 남긴다
   - IEND는 자바처럼 종류만 보고, 남긴 파일에는 규칙대로 쓴 12바이트를 넣는다. CRC가 빠진 IEND로 끝나는 PNG도 자바는 일부러 받기 때문이다 (PR 전 검토에서 찾음)
   - 조각 길이가 파일 끝을 넘는 깨진 PNG는 "읽을 수 없는 사진"(400)이다
2. 버리는 조각(글자, 색 정보 iCCP, gAMA, cHRM, sRGB, 해상도 pHYs, 만든 시각 tIME 같은 것)은 이 앱이 쓰지 않는다. 자바 소스(JDK 17)로도, 그림을 펼치는 코드는 IHDR, PLTE, tRNS에서 읽은 값만 쓰는 것을 확인했다
3. 견준 다른 후보: 압축한 조각의 합이나 개수가 한도를 넘으면 거절하기. 한도를 낮추면 보통 PNG도 거절하고, 높이면 여전히 모자랄 수 있어 고르지 않았다 (운영자 11-26)

## 전후

로컬, 힙 512 MB, SerialGC. 고치기 전(main `e2e16ec`)과 고친 뒤를 같은 시각에 번갈아 쟀다.

| | 고치기 전 | 고친 뒤 |
|---|---|---|
| 글자 조각이 큰 100 x 100 시험 PNG 셋, old 26 MiB와 190 MiB (6번) | OutOfMemoryError 6번 (550 ~ 1,242 ms) | **모두 보통처럼 처리** (345 ~ 399 ms) |
| 글자 조각이 깨진 148바이트 PNG | 400 (읽을 수 없는 사진) | 받음 |
| 보통 사진 9장(PNG 8, JPEG 1)의 본 사진과 썸네일 18개 | | 고치기 전과 바이트까지 같음 |
| 처리 시간, RGB 7071 x 7071 (2번 데운 뒤 5번의 가운데 값, 두 판) | 685, 690 ms | 690, 689 ms |
| 처리 시간, 화면 캡처 1179 x 2556 | 79, 82 ms | 82, 81 ms |
| 처리 시간, JPEG 12 MP | 411, 400 ms | 401, 403 ms |
| 처리 시간, XMP 30 KB가 든 PNG | 33, 34 ms | 28, 27 ms (글자 조각을 읽지 않음) |
| 운영 배포 (밖에서 1초마다 첫 화면과 썸네일 1,200번) | | 실패 0 |

- 시간 차이는 판마다 오르내리는 폭 안이다 (같은 코드의 두 판도 11 ms까지 다르다). 고친 코드가 더하는 일은 PNG를 한 번 훑고, 버릴 조각이 있을 때만 한 번 베끼는 것이다
- 색 프로필(iCCP)과 감마(gAMA, cHRM)를 일부러 sRGB와 멀게 넣은 PNG 둘도 결과가 바이트까지 같았다. 펼치는 코드가 이 값을 쓰지 않기 때문이다
- 덤: 종류 이름이 규칙에 맞지 않는 조각이나 IHDR 앞의 조각, CRC가 빠진 IEND가 있는 PNG는 고치기 전에는 위치와 촬영 시각을 잃었는데, 이제 읽는다 (PR 전 검토가 찾음)

## 재발 방지

- 테스트 15개를 더했다
  - `PngChunksTest` 9개: 쓰지 않는 조각 9가지를 넣었다 버리면 넣기 전 파일과 바이트까지 같다, eXIf와 PLTE, tRNS는 남긴다, 버릴 것이 없으면 베끼지 않는다, IEND 뒤의 바이트는 버린다, CRC가 빠졌거나 길이가 틀린 IEND는 규칙대로 다시 쓴다, 길이가 파일 끝을 넘으면 400
  - `ImageProcessorTest` 6개: PNG의 eXIf에서 위치와 촬영 시각을 읽고 저장하는 두 파일에는 GPS가 없다, 펼치기가 받는 파일은 조각을 버린 파일이다, 깨진 글자 조각이 든 RGB PNG도 받는다, 종류 이름에 숫자가 든 조각이 있어도 위치를 읽는다
  - 조각 버리기를 빼거나 머리 검사 뒤, 위치 읽기 뒤로 옮긴 코드로 돌리면 2 ~ 3개씩 실패하는 것을 봤다
- PR 전 검토 (에이전트 하나, JDK와 Thumbnailator, metadata-extractor 소스로 반례 찾기): CRC가 빠진 IEND를 400으로 거절하던 것과, 순서가 바뀌어도 통과하던 시험을 고쳤다
- 운영 로그의 `PNG chunks dropped` 줄로, 실제로 올라오는 PNG가 무엇을 버리는지 본다
- [prevent-photo-upload](prevent-photo-upload.md) 3번에 더했다

## 배운 것

- 그림의 크기 한도는 그림 밖의 데이터를 막지 못한다. 파일 안에 그림 말고 무엇이 들어 있고, 그것을 누가 읽는지를 따로 봐야 한다
- 같은 데이터를 읽는 곳이 여럿이면 그 앞에서 한 번 막는다. 글자 조각을 읽는 곳이 셋(자바의 PNG 읽기, 사진 정보 라이브러리, 썸네일 라이브러리)이라, 저마다 한도를 걸기보다 읽기 전에 쓰지 않는 조각을 버리는 쪽이 짧고 확실했다
- 앞에 검사를 더할 때는, 뒤의 라이브러리가 일부러 받는 것(CRC가 빠진 IEND)을 거절하지 않는지 소스로 확인한다
