# 글 상세 화면이 같은 분석 기록을 두 번 읽는다

- **종류**: 찾은 문제 (측정, 작음)
- **발견**: 2026-11-18, JM-91 기준선. 로컬에서 요청마다 쿼리 수를 셀 때
- **상태**: 할 일 (작은 개선. 쿼리 수를 테스트로 세는 일과 함께)
- **영향**: 지금은 거의 없다. 글 상세의 앱 쪽 시간은 p50 36 ms, p95 112 ms (CloudWatch 11-04 ~ 11-19). 쿼리가 하나 더 나갈 뿐이다

## 현상

로컬 서버와 로컬 MySQL로, 개발 설정이 찍는 SQL 로그를 traceId로 묶어 셌다 (11-18, 코드 `2df4fca`).

| 요청 | 쿼리 수 | 무엇 |
|---|---|---|
| 글 상세, 댓글 있음 (bot) | 6 | 글, 분석, **분석 한 번 더**, 댓글, 답글 한 번에, 댓글 수 |
| 글 상세, 댓글 없음 (bot) | 5 | 글, 분석, **분석 한 번 더**, 댓글, 댓글 수 |
| 글 상세, 댓글 있음 (사람) | 8 | 위 6개와 조회수 UPDATE, 방문 수 저장 |

피드는 글 24개에 쿼리 4개로 N+1이 없다 ([prevent-server-resources](prevent-server-resources.md)).

## 원인

`PostService.getDetail`이 사진을 가릴지 정하려고(JM-80) 분석 기록을 읽고, 화면의 분석 칸을 그리려고 `FoodAnalysisService.getView`가 또 읽는다. 두 메서드가 서로 다른 트랜잭션이라 JPA의 1차 캐시로도 한 번으로 합쳐지지 않는다.

## 앞으로 해결해 나갈 것

1. 분석 기록을 한 번 읽어 두 곳에 함께 넘긴다 (컨트롤러가 받은 것을 넘기거나, 한 서비스 메서드가 둘을 함께 돌려준다)
2. 피드와 글 상세의 쿼리 수를 테스트에서 세고, 늘면 테스트가 실패하게 한다 ([performance.md](../performance.md) 5절의 측정 조각 6)
3. 목표: 글 상세 쿼리 6개 → 5개 (사람이 열면 8개 → 7개)

## 재는 법

로컬 서버를 띄우고 bot User-Agent로 요청한 뒤, 응답 머리말 `X-Trace-Id`의 번호가 붙은 `org.hibernate.SQL` 줄을 센다 ([performance.md](../performance.md) 4.4).
