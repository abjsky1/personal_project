# 미리 막은 문제: 사진 올리기와 저장

- **종류**: 미리 막은 문제 (예방). 문제가 되기 전에 예상해서 만들어 둔 장치와, 그것이 실제로 어떻게 확인됐는지
- **정리**: 2026-11-19 (JM-91 측정과 대용량 사진 점검의 숫자로 확인). 시점은 각 장치를 처음 넣은 커밋

## 1. 휴대폰 사진이 한도에 막히거나 "연결 끊김"만 보는 문제 → 크기 한도를 네 겹으로

- **예상한 문제**: Spring의 기본 업로드 한도는 1 MB라 휴대폰 사진(보통 3 ~ 5 MB)이 거절된다. 한도를 넘은 요청은 Tomcat이 응답 없이 연결을 끊어, 사용자는 이유 없이 "연결이 끊겼습니다"만 본다
- **미리 한 것**: 브라우저가 보내기 전에 10 MB를 넘으면 알리고 막는다 (`posts/new.jsp`). 서버는 파일 10 MB, 요청 11 MB까지 받고(`spring.servlet.multipart`), Tomcat이 20 MB까지는 끝까지 받아 준 뒤 거절해서(`server.tomcat.max-swallow-size`) 우리 에러 화면("10MB까지")이 보인다. 그보다 크면 nginx가 413으로 끊는다(`client_max_body_size 20m`)
- **언제**: 2026-10-29 S1-1 (`88f7306`), nginx는 10-31 배포 구성 (`04894e8`)
- **확인**: 11-04 ~ 11-19에 서버의 10 MB 초과 거절 0건, nginx 413 1건 (대용량 사진 점검)
- **남은 것**: 브라우저가 10 MB에서 먼저 막은 수는 기록되지 않는다. 브라우저에서 줄여 보내는 방법은 [2026-11-18-upload-processing-slow](2026-11-18-upload-processing-slow.md)의 후보

## 2. 사진이 아닌 파일을 사진인 척 올리는 문제 → 파일 앞 바이트로 형식 검사

- **예상한 문제**: 확장자나 `Content-Type`은 보내는 쪽이 마음대로 바꿀 수 있다. 사진이 아닌 파일이 저장되거나, 깨진 파일을 펼치다 오류가 난다
- **미리 한 것**: 파일 맨 앞의 서명(매직 바이트)으로 JPEG, PNG만 받는다 (`ImageProcessor`). 받은 파일을 그대로 저장하지 않고 그림만 새 JPEG로 다시 써서 저장하므로, 원본 바이트에 숨긴 것이 저장소에 남지 않는다
- **언제**: 2026-10-29 S1-3 (`2f5cb1e`)
- **확인**: 11-13에 PNG라고 왔지만 내용이 PNG가 아닌 14 KB 파일이 34초 사이 두 번 거절됐다. 아이폰 HEIC 사진 2건(11-05, 11-11)도 거절되고 로그에 형식과 크기가 남았다
- **남은 것**: HEIC를 받을지는 거절 수를 보고 정한다 (대용량 사진 일)

## 3. 작은 파일이 서버 메모리를 다 먹는 문제 → 화소 수를 먼저 보고, 한 장씩 처리

- **예상한 문제**: 사진은 펼치면 화소 수만큼 메모리를 쓴다. 파일은 작아도 화소가 아주 많은 사진(이미지 폭탄)이나 큰 사진 여러 장이 동시에 오면 메모리 2 GB 서버가 멈출 수 있다
- **미리 한 것**: 사진 전체를 펼치기 전에 머리만 읽어 가로 x 세로가 5,000만 화소를 넘으면 거절한다 (`app.image.max-pixels`, `checkPixelCount`). 처리는 `synchronized`로 한 번에 한 장만 한다
- **언제**: 화소 검사 2026-10-29 S1-3 (`2f5cb1e`), 한 장씩 처리 10-31 배포 구성 (`04894e8`)
- **확인**: 2억 화소 합성 사진(73 MB)은 펼치지 않고 바로 거절됐다 (11-19 로컬 시험). 11-04 ~ 11-19 운영에서 올리기 500 0건, 화소 초과 0건
- **더 막은 것** (2026-11-20 ~ 22, JM-94, JM-105): 화소 수만으로는 메모리를 막지 못했다 ([큰 사진 메모리 부족](2026-11-19-large-photo-oom.md)). 큰 사진은 펼치면서 긴 변 2560으로 줄여 읽고, 펼치기 전에 머리만 읽어 펼친 크기(가로 x 세로 x 화소 하나의 바이트)가 1억 5천만 바이트를 넘거나 한 변이 65,535를 넘으면 거절한다 (`ImageProcessor`, PR #51, #53)
- **더 막은 것의 확인**: 로컬에서 old를 190 MiB 채운 힙 512 MB로 시험 사진 31장이 모두 처리되거나 거절됐다 (48MP, 50MP 세로의 최소 힙 896 ~ 1,024 MB → 320 MB). 11-18 ~ 11-25 운영 올리기 5xx 0건
- **남은 것**: 사진 처리의 다른 약점 2건(JM-108, JM-109)은 비공개 기록에 두고 고친다

## 4. 원본 사진이 저장과 전송을 키우는 문제 → 크게 받아 작게 보관

- **예상한 문제**: 휴대폰 원본(수 MB)을 그대로 두면 저장 공간과, 피드를 볼 때마다 보내는 양이 커진다
- **미리 한 것**: 원본은 저장하지 않는다. 긴 변 1280 JPEG(품질 0.85) 본 사진과 600 x 600 썸네일 두 장만 새로 만들어 저장한다 (`ImageProcessor`)
- **언제**: 2026-10-29 S1-3 (`2f5cb1e`)
- **확인**: 실제 사이트 사진 139장(11-19): 본 사진 평균 207 KB, 썸네일 평균 79 KB, 글 하나에 약 286 KB. 합성 12MP 사진은 4.6 MB → 약 192 KB로 약 **96% 줄었다** (로컬). S3 전체가 약 43.7 MB라 저장 비용은 한 달 0.001달러 수준이다
- **남은 것**: 썸네일이 휴대폰 칸보다 커서 피드 1쪽이 1.97 MB다 → [2026-11-18-photo-transfer-slow](2026-11-18-photo-transfer-slow.md)

## 5. 사진 속 위치가 새어 나가는 문제 → EXIF를 지우고, 위치는 동의한 경우만

- **예상한 문제**: 휴대폰 사진 파일에는 GPS 좌표와 기기 정보(EXIF)가 들어 있어, 사진을 받은 사람이 찍은 곳(집 등)을 알 수 있다
- **미리 한 것**: 사진을 새로 쓸 때 EXIF를 옮기지 않아 위치가 사라진다. 지우기 전에 방향 정보만 반영해 세로 사진이 눕지 않게 한다. 위치와 촬영 시각은 올리는 사람이 동의한 경우에만 DB에 저장하고, 통계에서는 좌표를 내보내지 않는다 (JM-85)
- **언제**: EXIF 지우기 2026-10-29 S1-3 (`2f5cb1e`), 동의한 경우만 저장 10-30 S1-4 (`3ec563b`)
- **확인**: 저장된 사진 파일에 위치와 기기 정보가 없음을 11-19 점검에서 확인했다

## 6. 다른 사람의 사진이나 서버 파일을 짐작해서 꺼내는 문제 → 무작위 이름과 이름 검사

- **예상한 문제**: 사진 이름이 1, 2, 3처럼 차례 번호면 남의 사진을 짐작해서 열 수 있다. `../application.properties` 같은 이름으로 다른 파일을 꺼내려는 시도(경로 조작)도 있다
- **미리 한 것**: 사진 이름은 무작위 UUID(122비트)로 만든다. 사진 주소(`GET /images/{이름}`)는 이름이 UUID 모양이 아니면 아예 찾지 않는다 (`ImageController`의 `KEY_PATTERN`)
- **언제**: 2026-10-31 배포 준비 (`2f67cb2`)
- **확인**: 없는 이름과 모양이 다른 이름은 404 (11-19 점검)

## 7. 저장소가 통째로 공개되거나 열쇠가 새는 문제 → 비공개 버킷, 앱을 거쳐 전달, 열쇠 없는 역할

- **예상한 문제**: S3 버킷을 공개하면 누구나 목록과 사진을 받는다. 코드나 설정 파일에 AWS 열쇠를 적으면 저장소가 새어 나갈 때 함께 샌다
- **미리 한 것**: 버킷은 공개하지 않고, 브라우저는 S3가 아니라 앱의 `/images/`를 거쳐 사진을 받는다. 앱은 EC2에 붙인 IAM 역할로 S3에 접근해서 코드와 설정 어디에도 열쇠가 없다 (`S3ImageStorage`). 역할은 `images/` 아래의 읽기와 쓰기, 목록만 할 수 있고 지우기는 못 한다
- **언제**: 2026-10-31 배포 준비 (`2f67cb2`), 버킷과 역할은 11-03 S4-3
- **확인**: 11-19 콘솔 점검에서 퍼블릭 액세스 차단 네 가지가 모두 켜져 있었다
- **남은 것**: 저장소가 털렸을 때를 더 단단히 막는 일은 진행 중이다. 점검에서 찾은 것은 고친 뒤에 전후로 적는다

## 8. 같은 사진을 매번 다시 받는 문제 → 1년 캐시

- **예상한 문제**: 피드를 열 때마다 사진을 다시 받으면 서버와 휴대폰 데이터를 낭비한다
- **미리 한 것**: 사진 응답에 1년 캐시(`Cache-Control: public, max-age=1년, immutable`)를 붙인다. 사진 이름이 무작위라 같은 이름의 내용이 바뀌는 일이 없어 오래 저장해도 안전하다
- **언제**: 2026-10-31 배포 준비 (`2f67cb2`)
- **나눈 것** (2026-11-26, JM-95): 1년 캐시는 보이는 글의 사진에만 붙인다. 지운 글과 가린 글의 사진, 어느 글의 사진도 아닌 파일은 404와 `no-store`라 브라우저가 기억하지 않는다 (10번)
- **남은 것**: 처음 들어온 사람은 여전히 다 받아야 한다 → [2026-11-18-photo-transfer-slow](2026-11-18-photo-transfer-slow.md)

## 9. 도배로 저장 공간과 AI 비용을 다 쓰는 문제 → 올리기 횟수 제한

- **예상한 문제**: 누군가 스크립트로 사진을 계속 올리면 저장 공간과 하루 AI 분석 한도, 비용이 바닥난다
- **미리 한 것**: 처음에는 IP마다 1분 3번, 하루 30번으로 막았다 (2026-10-30, `c0671b2`). 11-13 발표에서 같은 와이파이를 쓰는 20명 가까이가 한도 하나를 나눠 쓰다 막히자(JM-79), 브라우저(세션)마다 1분 5번, 하루 30번으로 세고 IP와 전체에는 하루 상한(200, 500)만 두도록 바꿨다 (`f92389f`)
- **확인**: 11-04 ~ 11-19 횟수 제한(429)에 걸린 올리기 8건
- **남은 것**: 횟수는 서버 메모리에 있어 배포하면 처음부터 다시 센다 ([2026-11-10-deploy-502](2026-11-10-deploy-502.md)의 3)

## 10. 지운 글과 가린 글의 사진이 예전 주소로 열리는 문제 → 보이는 글의 사진만 보내고, 관리자 주소를 따로

- **예상한 문제**: 글을 지우거나 사진을 가려도(JM-80) 사진 파일은 저장소에 남는다. 사진 주소가 파일만 보고 보내면, 예전 주소를 아는 사람(지우기 전에 본 사람, 브라우저 기록)은 계속 볼 수 있다. 피드와 글 화면이 그 주소를 쓰지 않는 것만으로는 막히지 않는다
- **막은 것**: 처음에는 없었다. 2026-11-19 점검에서 지운 글 20개의 사진 40장이 열리는 것을 찾아 11-26에 고쳤다 ([찾은 문제](2026-11-19-deleted-post-photos-open.md)). 사진 주소(`GET /images/{이름}`)가 사진 이름으로 글을 찾아, 지우지 않았고 가리지 않은 글의 사진만 보내고 나머지는 404와 `no-store` (`PhotoVisibility`, SQL 한 문장, 색인 둘). 가리는 기준은 피드와 같은 `Post.isPhotoHeld`라 한쪽만 바뀌지 않는다. 관리자 화면은 `/admin/images/{이름}` (관리자로 로그인한 브라우저에만, `no-store, private`)
- **언제**: 2026-11-26 JM-95 (PR #63, `5b4b512`)
- **확인**: 운영에서 지운 글의 사진 40장이 200 → 404, 보이는 사진은 200 그대로 (서버에서 같은 점검을 전후로). 테스트가 지운 글 둘, 가린 글과 올린 뒤, 주인 없는 파일, 관리자 주소의 로그인 전후를 보고, 고친 줄을 빼면 그중 3개가 실패한다 (`ImageControllerTest`, `PhotoVisibilityTest`, `AdminPageTest`)
- **남은 것**: 지우기 전에 이미 받은 브라우저의 사본은 1년 캐시로 남는다 (8번, 운영자 결정으로 그대로). 지운 글의 사진 파일은 S3에 남고, 언제 지울지는 정하지 않았다 (앱 역할에는 지우기 권한이 없다, 7번). 사진 여러 장 올리기(JM-56)처럼 사진 이름이 다른 표에 생기면 글 찾기도 그 표를 봐야 한다 (빠뜨리면 그 사진은 404라 새지는 않는다)
