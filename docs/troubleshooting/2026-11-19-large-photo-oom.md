# 화소 한도 안의 큰 사진이 메모리 부족으로 실패했다

- **종류**: 찾은 문제 (점검). 누가 일부러 되풀이하면 서비스를 막을 수 있는 약점이라, 고칠 때까지 비공개 기록 저장소에 두었다가 2026-11-25 공개
- **발견**: 2026-11-19, 대용량 사진 점검 (로컬에서 운영과 같은 힙으로 재현). 남은 경우는 JM-94의 PR 전 검토에서 찾았다
- **상태**: 해결 (JM-94 PR #51, 2026-11-20 배포. JM-105 PR #53, 2026-11-22 배포)
- **영향** (고치기 전): 화소 한도(5,000만)와 파일 한도(10 MB)를 모두 지나는 사진 가운데 일부가 운영과 같은 힙(512 MB)에서 `OutOfMemoryError`로 실패했다. 사용자는 500 화면을 봤다
  - 4,800만 ~ 5,000만 화소 세로 사진 (8 MB 파일로도)
  - 아주 넓은 사진 (긴 변 10240을 조금 넘음)
  - 펼치면 큰 투명 PNG
  - 사진 처리는 한 번에 한 장이라, 이런 사진을 되풀이해 올리면 그동안 다른 사람의 올리기도 막힐 수 있었다. 11-04 ~ 11-19 운영에서 올리기 500은 0건이었다 (일어나기 전에 찾음)

## 현상

로컬에서 운영과 같은 조건(Corretto 17, `-Xmx512m`, SerialGC)으로 그때 코드의 사진 처리를 돌려, 처리가 성공하는 가장 작은 힙을 쟀다 (합성 사진):

| 사진 (모두 화소 한도와 10 MB 안) | 필요한 최소 힙 | 512 MB에서 |
|---|---|---|
| 12MP 세로 4032 x 3024 | 256 MB | 성공 |
| 24MP 세로 | 512 MB | 성공 (빠듯함) |
| **48MP 세로** 8064 x 6048 | **896 MB** | **실패** |
| **50MP 세로** 8160 x 6120 | **1,024 MB** | **실패** |
| 한 색 JPEG 10241 x 4882 세로 (785 KB) | 896 MB | 실패 |
| 투명 PNG 10241 x 4882 (231 KB) | 768 MB | 실패 |
| 16비트 투명 PNG 7071 x 7071 (627 KB) | 896 MB | 실패. 메모리 부족을 "JPEG 또는 PNG 사진만"이라는 틀린 안내(400)로 감췄다 |

- 시험 프로그램만 있는 JVM의 숫자라, 앱이 이미 쓰는 힙이 있는 운영은 더 빠듯하다
- 운영 힙을 서버에서 확인했다 (11-20, `jcmd`): SerialGC, 최대 힙 512 MiB 가운데 old 최대 341 MiB, 잰 때 old 사용 190 MiB. 48MP 사진을 펼친 그림 한 장(약 140 MiB)은 young보다 커서 바로 old에 놓인다

## 원인

- 화소 검사는 가로 x 세로만 봤지만, 실제 메모리는 원본을 원래 크기로 펼친 그림에 더해 세로 사진이면 EXIF 방향대로 돌린 그림을 한 장 더 만들어 두 배 가까이 들었다
- 줄이는 라이브러리(Thumbnailator)는 "목표 x 2의 거듭제곱" 크기의 임시 그림을 원본과 같은 형식으로 만든다. 긴 변이 10240(2560 x 4)을 조금 넘으면 임시 그림이 원본만큼 커졌다
- 투명 PNG는 화소마다 4바이트, 16비트 PNG는 8바이트로 펼쳐진다. 화소 수가 같아도 펼친 크기는 몇 배다
- 힙 512 MB는 12MP 세로 사진을 기준으로 정한 값이라 화소 한도 끝의 사진은 들어가지 않았다

## 해결

1. **JM-94** (PR #51, 11-20): 긴 변이 2560보다 긴 사진은 펼치면서 2560으로 줄이고, 줄인 그림을 방향대로 돌린다. 저장하는 사진(긴 변 1280, 썸네일 600 x 600)의 크기는 그대로다
2. **JM-105** (PR #53, 11-22): 펼치기 전에 머리만 읽어 펼친 크기(가로 x 세로 x 화소 하나의 바이트)가 1억 5천만 바이트를 넘으면 거절하고, 사진 칸 아래에 "사진이 너무 큽니다. 가로, 세로 크기를 줄여서 올려 주세요. PNG는 JPEG로 바꿔 올려도 됩니다."를 보여 준다
   - 자바가 바로 줄이지 못하는 형식(16비트, 회색+투명, 1 ~ 4비트 팔레트 PNG, CMYK JPEG)은 줄이는 동안 원본 전체의 복사본이 생겨 화소당 8바이트를 더 센다
   - 한 변 65,535 한도 (PNG의 한 줄 버퍼)
   - 긴 변 10240 이상은 줄이는 목표를 2의 거듭제곱에 맞춰 첫 임시 그림을 원본의 4분의 1로
   - PNG를 읽다 메모리가 모자라면 400으로 감추지 않고 에러 로그에 남긴다
   - 후보 넷을 운영처럼 old를 190 MiB 채운 시험으로 견줘, 휴대폰 사진은 그대로 두고 코드가 가장 짧은 안을 운영자가 골랐다

## 전후

로컬, 같은 도구로 전과 후를 번갈아 잼 (힙 512 MB, SerialGC):

| 사진 | 처리 시간 전 → 후 | 최소 힙 전 → 후 |
|---|---|---|
| 12MP 세로 | 832 → 538 ms | 256 → 160 MB |
| 24MP 세로 | 1,350 → 871 ms | 512 → 256 MB |
| 48MP 세로 | 실패 → 1,297 ms | 896 → 320 MB |
| 50MP 세로 | 실패 → 1,309 ms | 1,024 → 320 MB |
| 한 색 JPEG 10241 x 4882 세로 | 1,346 ~ 1,968 → 730 ~ 856 ms (JM-105 전후) | 896 → 512 MB (JM-94) → 256 MB (JM-105) |
| 투명 PNG, 16비트 PNG | 실패 (500 또는 틀린 안내) | 머리만 읽고 거절 (새 안내) |

- old를 190 MiB 채운 가장 나쁜 경우: 시험 사진 31장이 모두 처리되거나 머리만 읽고 거절됐다. 받는 사진의 최소 힙은 모두 320 MB 이하
- 실제 앱(war, 힙 512 MB)으로 올리기: 48MP, 50MP 세로와 넓은 한 색 JPEG의 500이 302로, 16비트 PNG의 틀린 안내가 새 안내로 바뀌었다. 앱 로그의 `OutOfMemoryError` 0줄
- 화질: 저장되는 본 사진은 가로 사진이 화소까지 같고, 세로 사진은 PSNR 50 dB를 넘는다. 휴대폰 사진과 정사각 50MP는 JM-105 전후의 결과 파일이 바이트까지 같다
- **운영** (CloudWatch 앱 쪽 시간, [performance.md](../performance.md) 4.1): 글 올리기 p50 1,453 ms (11-04 ~ 11-18, 143건) → 1,318 ms (11-18 ~ 11-25, 33건), JM-105 배포 뒤만 1,183 ms (11건). p95는 4,540 → 4,959 ms로, 건수가 적어 p95가 가장 느린 한두 건이다. 같은 7일 동안 올리기 5xx 0건, 메모리 부족 0건

## 재발 방지

- 테스트: 큰 세로 사진을 줄여 읽기, 펼친 크기 한도와 형식별 바이트, 한 변 한도, 머리만 있는 PNG가 400, 메모리 부족을 감추지 않기 (`ImageProcessorTest`)
- [prevent-photo-upload](prevent-photo-upload.md) 3번을 이 숫자로 고쳤다
- 사진 처리의 다른 약점 2건(JM-108, JM-109)은 이 점검과 검토에서 찾았고, 고칠 때까지 비공개 기록에 둔다

## 배운 것

- 화소 수 한도는 메모리 한도가 아니다. 펼친 형식(화소 하나의 바이트)과 라이브러리가 만드는 임시 그림까지 세야 한다
- 메모리 시험은 앱이 이미 쥔 힙을 채운 상태(운영의 old 사용)로 해야 운영과 같다. 빈 JVM에서는 되는 사진이 운영에서는 실패한다
- 예외를 다른 예외로 감싸는 라이브러리(자바의 PNG 읽기)는 원인을 숨긴다. 감싼 예외 안까지 보고 다르게 다룬다
