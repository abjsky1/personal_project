# 지운 글과 가린 글의 사진이 예전 주소로 열렸다

- **종류**: 찾은 문제 (점검). 개인정보 약점이라, 고칠 때까지 비공개 기록 저장소에 두었다가 2026-11-26 공개
- **발견**: 2026-11-19, 사진 저장소 보안 점검
- **상태**: 해결 (JM-95 PR #63, 2026-11-26 배포)
- **영향** (고치기 전): 작성자나 운영자가 지운 글의 사진을, 예전 주소를 아는 사람은 계속 볼 수 있었다. 사용자는 "지웠다"고 믿는다
  - 사진 이름은 무작위(UUID, 122비트)라 짐작으로는 못 찾는다. 지우기 전에 본 사람, 브라우저 기록, DB를 본 사람처럼 이름을 아는 사람만 열 수 있었다
  - 사진 검토로 가린 글(JM-80)의 사진도 주소를 알면 똑같이 열렸다. 운영에는 11-19와 11-26 모두 가린 글이 없었다
  - 피드와 글 화면은 지운 글과 가린 글의 사진 주소를 쓰지 않아서, 화면으로는 막힌 것처럼 보였다

## 현상

- 11-19 점검: 사이트에 보이는 글 139개의 사진 278장과 S3의 파일 318개를 맞춰 보니, 40장(3,831 KB)이 어디에도 걸려 있지 않았다. 피드에 없는 글 20개의 사진이고, 그 글 화면은 404였다. 그중 두 장의 예전 주소를 요청하자 둘 다 200이었다 (사진 그대로)
- 그 응답에 1년 공개 캐시(`Cache-Control: max-age=31536000, public, immutable`)가 붙어, 이미 받은 브라우저의 사본은 우리가 지울 수 없다
- 내 PC 재현 (11-25): 시험 글로 작성자가 지운 글, 가린 글, 보이는 글을 만들어 본 사진과 썸네일을 요청하니, 여섯 장 모두 200과 1년 캐시였다
- 11-26 고치기 전, 서버에서 지운 글 20개(작성자 12, 운영자 8)의 본 사진과 썸네일 40장을 모두 요청했다. 40장 모두 200이고, 보이는 글의 썸네일(대조 20장)과 시간도 같았다 (평균 0.079초, 0.082초)

## 원인

- 사진 주소(`GET /images/{이름}`, `ImageController`)는 이름이 UUID 모양인지만 보고 저장소에서 꺼내 줬다. 그 사진의 글이 지워졌는지, 가려졌는지는 보지 않았다
- 글을 지우면 상태만 바뀌고 S3의 사진은 남는다 (기획서 5.1절, 지운 글도 보존). 기획서에 "S3에서 직접 URL 접근을 막을지는 S4에서 검토"로 미뤄 둔 일이, S4에서 사진을 앱을 거쳐 보내게 바꾼 뒤에도 그대로 남았다. 앱을 거치게 되면서 막을 자리가 생겼는데, 그 자리에서 글을 보지 않았다

## 해결 (JM-95, PR #63)

1. `/images/{이름}`이 사진 이름으로 글을 찾아, 지우지 않았고 사진을 가리지 않은 글의 본 사진과 썸네일만 보낸다
   - 지운 글과 가린 글의 사진, 어느 글의 사진도 아닌 파일은 404다. 404에는 `no-store`를 붙여, 가렸던 사진을 운영자가 올리면 같은 주소가 바로 열린다
   - 가리는 기준은 피드가 쓰는 `Post.isPhotoHeld`를 같이 쓴다. 분석 기록이 없는 글도 피드와 같게 본다
   - 글 찾기는 `PhotoVisibility`가 SQL 한 문장으로 한다 (JdbcTemplate, 트랜잭션 없이). posts의 `image_key`, `thumbnail_key`에 색인 둘을 더했다 (배포 때 ddl-auto가 만든다)
2. 관리자 화면은 새 주소 `/admin/images/{이름}`으로 지운 글과 가린 글의 사진도 본다. 관리자로 로그인한 브라우저에만 보내고, 브라우저에 남기지 않는다 (`no-store, private`)
3. 그대로 둔 것 (운영자 결정)
   - 보이는 사진의 1년 캐시. 지우기 전에 이미 받은 브라우저의 사본은 남는다
   - 지운 글의 S3 파일은 지우지 않는다. 지금 앱 역할에는 지우기 권한이 없고, 언제 지울지는 따로 정한다

## 전후

| | 고치기 전 | 고친 뒤 |
|---|---|---|
| 운영, 지운 글 20개의 사진 40장 (서버에서 요청) | 200 40장, 평균 0.079초 | **404 40장**, 평균 0.025초 |
| 운영, 보이는 글의 썸네일 20장 (대조) | 200 20장, 평균 0.082초 | 200 20장, 평균 0.085초 |
| 운영, posts의 색인 | `PRIMARY`, `idx_posts_status_id` | 더함: `idx_posts_image_key`, `idx_posts_thumbnail_key` |
| 로컬, 지운 글과 가린 글의 사진 4장 | 200, 1년 캐시 | 404, `no-store`. 가린 글은 운영자가 올리면 200 |
| 로컬, 사진 요청 한 번에 DB가 받는 문장 | 0 | 1 (MySQL general log) |
| 로컬, 사진 한 장의 앱 쪽 시간 p50 (썸네일 하나씩 240번, 두 판) | 1.0, 0.5 ms | 2.0 (서버를 켠 직후), 1.0 ms |

- 404는 S3에서 사진을 읽지 않고 본문도 비어서 더 빠르다
- 글 찾기 한 번은 로컬 0.39 ms다 (두 색인을 합쳐 쓴다). 따로 만든 DB에 글 10만 개를 넣으면 색인 없이 13 ~ 25 ms, 색인 둘이면 0.26 ~ 0.37 ms
- 사진 한 장에 0.5 ~ 1 ms가 더해졌다. 운영의 앱 쪽 사진 p50은 92 ms(대부분 S3에서 받는 시간)라 1% 안팎이다. 보이는 썸네일의 +3 ms는 20장을 한 번씩 잰 것이라 흔들림과 가를 수 없다
- 배포하는 동안 바깥에서 1초마다 첫 화면과 썸네일을 모두 1,200번 열어 실패는 0이었다
- 남은 숫자: 운영의 앱 쪽 사진 p50, p95(CloudWatch)를 배포 뒤 7일로 배포 전 7일(p50 92 ms, p95 799 ms)과 견준다. S8 마감 때 이 표에 더한다 (같은 주에 썸네일 일 JM-102가 배포되면 날짜를 나눠 본다)

## 재발 방지

- 테스트
  - `ImageControllerTest`: 보이는 글, 분석 중인 글, 운영자가 올린 글은 200과 1년 캐시. 작성자와 운영자가 지운 글, 가린 글은 파일이 그대로 있어도 404와 `no-store`, 가린 글을 올리면 200. 주인 없는 파일, 파일 없는 글, 이름 모양이 다른 것은 404. 색인 둘이 있는지
  - `PhotoVisibilityTest`: 분석 상태 값마다, 지운 상태 둘
  - `AdminPageTest`: 관리자 사진 주소는 로그인 전 로그인 화면으로 가고, 로그인 뒤 가린 글과 지운 글의 사진을 `no-store, private`로 보낸다. 같은 사진의 공개 주소는 404. `AdminPageDisabledTest`: 관리자 화면이 꺼지면 404
  - 고친 줄(공개 주소의 글 확인)을 잠깐 빼면 지운 글, 가린 글, 주인 없는 파일의 테스트 3개가 실패하는 것을 봤다
- PR 전 검토 (에이전트 둘, 접근 규칙과 캐시, DB와 배포): 고칠 결함 없음
  - 관리자 주소를 로그인 없이 열려는 주소 변형 15가지(인코딩, 점과 빗금, 대소문자, 뒤에 붙인 것)와 공개 주소의 이름 변형 7가지가 모두 막혔다
  - 동시에 200개까지 350번 보내도 모두 200이고, DB 연결이 새지 않았다
- [prevent-photo-upload](prevent-photo-upload.md) 10번에 더했다

## 배운 것

- 화면이 주소를 쓰지 않는 것과 주소가 막힌 것은 다르다. 지운 글을 피드에서 빼도 사진 주소는 따로 열린다. 공개 주소마다 무엇을 보고 보내는지를 따로 확인해야 한다
- 미뤄 둔 검토는 구조를 바꿀 때 다시 꺼내 봐야 한다. S3 직접 주소에서 앱을 거쳐 보내기로 바꾸면서 막을 자리가 생겼는데, "S4에서 검토"는 그대로 잊혔다
- 오래 두는 캐시는 되돌릴 수 없다. 1년 캐시를 붙이기 전에, 그 응답을 나중에 숨길 일이 있는지 먼저 정한다 (그래서 404는 `no-store`)
