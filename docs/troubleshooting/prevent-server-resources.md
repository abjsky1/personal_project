# 미리 막은 문제: 서버 자원, 배포, 비용

- **종류**: 미리 막은 문제 (예방). 문제가 되기 전에 예상해서 만들어 둔 장치와, 그것이 실제로 어떻게 확인됐는지
- **정리**: 2026-11-19 (JM-91 측정의 숫자로 확인). 시점은 각 장치를 처음 넣은 커밋

## 1. 2 GB 서버에 Spring과 DB를 같이 두면 메모리가 모자라는 문제 → DB를 RDS로 뺌

- **예상한 문제**: 처음에는 서버 안 Docker MySQL을 쓰려 했다
- **미리 한 것**: 내 PC Docker에서 메모리를 재 보니 app 약 650 MB(큰 사진 처리 직후), MySQL 약 460 MB라 2 GB 서버에 여유가 없었다. 운영 DB를 AWS가 관리하는 RDS(db.t4g.micro)로 뺐다. 덤으로 자동 백업이 생기고, 서버를 지워도 DB가 남는다
- **언제**: 2026-10-31 결정 (기획서 18절), 11-03 S4-3에 만듦
- **확인**: 11-18 서버 메모리 1,909 MB 중 사용 685 MB, 가용 1,071 MB. RDS CPU 평균 3.94%, 최대 7.97% (CloudWatch 2주)

## 2. 자바가 메모리를 끝없이 늘려 서버 전체가 멈추는 문제 → 힙, 컨테이너, 스왑의 세 겹 한도

- **예상한 문제**: JVM이 메모리를 늘리다 운영체제와 nginx까지 밀어내면 서버 전체가 멈춘다
- **미리 한 것**: 힙을 512 MB로 묶고(`JAVA_TOOL_OPTIONS: -Xmx512m`), app 컨테이너 전체를 1 GB로 묶어(`mem_limit: 1g`) 넘으면 app만 꺼졌다 다시 켜진다. 서버에는 스왑 2 GB를 두어 순간적인 부족에 버틴다
- **언제**: 힙과 컨테이너 한도 2026-10-31 (`04894e8`), 스왑 11-03 S4-3
- **확인**: 11-18 app 컨테이너 404 MiB / 1 GiB, 스왑 26 MB 사용. EC2 CPU 평균 0.85%, 크레딧은 거의 그대로 (2주)
- **남은 것**: 사진 처리의 메모리는 대용량 사진 점검에서 다시 보고 있다 ([prevent-photo-upload](prevent-photo-upload.md)의 3)

## 3. 로그가 디스크를 가득 채우는 문제 → 로그 크기 한도와 이미지 정리

- **예상한 문제**: 컨테이너 로그는 그대로 두면 끝없이 쌓여 디스크(20 GB)가 차고 서버가 멈춘다. 배포마다 받은 이미지도 쌓인다
- **미리 한 것**: nginx와 certbot 로그는 10 MB 파일 세 개까지만 남긴다(json-file). app 로그는 CloudWatch로 보낸다(90일). 배포가 끝나면 쓰지 않는 이미지를 지운다(`docker image prune -af`)
- **언제**: 로그 한도 2026-10-31 (`04894e8`), CloudWatch 11-04 S4-6 (`d5a7451`), 이미지 정리 11-04 S4-5 (`781e852`)
- **확인**: 켜진 지 15일, 배포 18번 뒤 디스크 20 GB 중 5.9 GB (30%, 11-18)
- **남은 것**: nginx 기록은 서버 안에만 있어 컨테이너를 새로 만들면 사라진다. CloudWatch로 보내는 일이 JM-91의 첫 조각이다

## 4. 배포가 잘못돼도 모르고 넘어가는 문제 → 상태 검사, 기다렸다 확인, 되돌리기

- **예상한 문제**: 새 app이 뜨지 못했는데 배포가 "성공"으로 끝나면 사이트가 멈춘 채 아무도 모른다
- **미리 한 것**: app에 30초마다 상태 검사(`/actuator/health`)를 두고, 배포 스크립트가 healthy가 될 때까지 최대 2분 기다린다. 2분이 지나면 최근 로그를 찍고 실패로 멈춘다. 이미지는 커밋마다 GHCR에 남아 있어 `bash deploy.sh <예전 SHA>`로 1분 안에 되돌린다
- **언제**: 상태 검사 2026-10-31 (`04894e8`), 기다리기와 되돌리기 11-04 S4-5 (`781e852`)
- **확인**: 11-19 PR #49 배포에서 app이 새 이미지(`8ddfd4a`)로 healthy가 된 것을 서버에서 확인했다
- **남은 것**: 배포하는 20초 동안의 502 → [2026-11-10-deploy-502](2026-11-10-deploy-502.md)

## 5. 서버가 다시 켜지면 사이트가 멈춘 채 남는 문제 → 자동 복구

- **예상한 문제**: AWS가 서버를 다시 켜거나 운영자가 재부팅하면 컨테이너가 꺼진 채 남는다
- **미리 한 것**: 모든 컨테이너에 `restart: unless-stopped`를 두었다
- **언제**: 2026-10-31 (`04894e8`)
- **확인**: 11-03 S4-3에서 재부팅 1분 뒤 컨테이너가 스스로 올라오고 스왑도 남는 것을 확인했다

## 6. 배포로 app 주소가 바뀌면 502가 계속되는 문제 → nginx가 주소를 다시 묻게

- **예상한 문제**: nginx는 켜질 때 알아낸 app 주소를 계속 쓴다. 배포로 app 컨테이너가 새로 만들어져 주소가 바뀌면 502가 계속된다
- **미리 한 것**: Docker 안의 이름 풀이 서버에 10초마다 다시 묻게 하고(`resolver 127.0.0.11 valid=10s`), 배포 스크립트도 끝에 nginx를 다시 읽게 한다
- **언제**: 2026-11-04 S4-5 (`781e852`)
- **확인**: 처음 두 번은 설정이 실제로 적용되지 않았다 ([2026-11-04-nginx-bind-mount-stale](2026-11-04-nginx-bind-mount-stale.md)). 고친 뒤 배포 18번에서 502는 배포하는 순간에만 났고 계속되지 않았다

## 7. 배포 뒤에도 옛 CSS가 보이는 문제 → CSS 주소에 내용 지문

- **예상한 문제**: 브라우저는 한 번 받은 CSS를 저장해 두고 다시 쓴다. 배포로 CSS를 바꿔도 옛 모양이 보인다 (개발 중에 실제로 겪었다)
- **미리 한 것**: 운영에서는 CSS 주소에 파일 내용의 지문을 붙인다(`/css/app-3f2a….css`). 내용이 바뀌면 주소가 바뀌므로 1년 캐시를 걸어도 안전하다
- **언제**: 2026-10-31 (`04894e8`)

## 8. 요청을 처리하는 동안 DB 연결이 모자라는 문제 → open-in-view 끄기

- **예상한 문제**: 기본 설정은 화면(JSP)을 다 그릴 때까지 DB 연결을 붙잡는다. 느린 요청이 몰리면 연결 풀(10개)이 바닥난다
- **미리 한 것**: `spring.jpa.open-in-view=false`로 서비스가 끝나면 연결을 바로 돌려준다
- **언제**: 2026-10-28 개발 환경 (`599cf75`)
- **확인**: RDS 연결 수 평균 10 (연결 풀 크기), 최대 20은 배포 순간 (2주)

## 9. 글 수만큼 쿼리가 늘어나는 문제 (N+1) → 화면의 글들 것을 한 번에

- **예상한 문제**: 피드 카드마다 분석 결과와 댓글 수를 따로 읽으면 글 24개에 쿼리가 48번 더 나간다
- **미리 한 것**: 한 쪽의 글 번호를 모아 분석은 `findAllById` 한 번, 댓글 수는 `group by` 한 번으로 읽는다 (`PostService.summariesOf`). 답글도 화면의 댓글들 것을 한 번에 읽는다
- **언제**: 분석 2026-11-02 S2-3 (`7bffd3f`), 댓글 수 11-04 S3-1 (`97723d9`), 답글 11-11 (PR #27, JM-58)
- **확인**: 피드 1쪽(글 24개)이 쿼리 4개로 끝난다 (11-18 로컬). 피드의 앱 쪽 시간 p95 64 ms (CloudWatch 11-04 ~ 11-19)
- **남은 것**: 글 상세가 분석 기록을 두 번 읽는 작은 중복 → [2026-11-18-detail-reads-analysis-twice](2026-11-18-detail-reads-analysis-twice.md)

## 10. AI 분석이 올리기를 붙잡고 비용이 넘치는 문제 → 요청 밖에서 분석, 일꾼과 줄과 하루 한도

- **예상한 문제**: AI(Gemini)가 답하는 데 몇 초가 걸린다. 올리기 요청 안에서 기다리면 사용자가 그만큼 더 기다리고, 몰리면 서버 스레드가 묶인다. 분석이 끝없이 늘면 비용도 넘친다
- **미리 한 것**: 글은 먼저 저장하고 분석은 뒤에서 한다. 일꾼 스레드 2개가 동시에 분석하고 나머지는 줄(최대 50건)에서 기다린다. 하루 전체 분석 수에 상한(처음 200, 11-13부터 500)을 두어 넘으면 분석하지 않는다
- **언제**: 뒤에서 분석과 일꾼 2026-11-02 S2-2 (`0d6f7e4`), 하루 상한 11-02 S2-4 (`eb65ada`)
- **확인**: AI 분석 p50 2.4초, p95 4.1초인데 올리기 응답은 이를 기다리지 않는다. 30일 152건, 성공률 100%, 실패 0. 한 달 비용은 AWS 약 45달러에 AI는 1,000건에 1달러 안팎 (11-05 점검, AI 모델 비교 문서)

## 11. 모르는 사이 요금이 크게 나오는 문제 → 요금 알림과 월 1회 점검

- **예상한 문제**: 지운 줄 알았던 자원이나 실수로 만든 자원이 몰래 요금을 낸다
- **미리 한 것**: AWS 요금 알림 50달러를 걸고(S4-2), 한 달에 한 번 청구서에서 켜 둔 자원("Hrs", "GB-Mo" 줄)만 본다 (기획서 16절 "비용 점검")
- **언제**: 2026-11-02 S4-2, 첫 점검 11-05
- **확인**: 첫 점검에서 남은 자원이 없고 추정과 같은 월 약 45달러였다. EC2 크레딧 초과로 낸 돈 0 (2주)

## 12. 화면마다 쓰는 기록이 응답을 늦추는 문제 → 응답 밖에서 한 문장으로

- **예상한 문제**: 사용자 흐름(JM-92)은 사람이 화면을 받을 때마다 DB에 한 줄을 쓴다. 화면을 다 그린 뒤에 써도 응답의 끝은 그 뒤에 나가서, 쓰는 시간만큼 사람이 기다린다. 쓰기는 COMMIT마다 디스크에 기록을 확정해서(MySQL 기본값, RDS도 같다) 읽기보다 느리다
- **미리 한 것**: 처음에는 JPA로 저장했다가, 재어 보고 두 번 고쳤다. ① JPA는 트랜잭션 때문에 문장이 네 번 가서(`SET autocommit=0`, INSERT, `COMMIT`, `SET autocommit=1`) INSERT 한 문장으로 바꿨다 (JdbcTemplate, autocommit). ② 그래도 사람이 기다리는 시간이 남아서, 저장을 응답 밖으로 뺐다: 인터셉터는 줄에 넣기만 하고, 기록 전용 일꾼 스레드 하나가 차례로 저장한다. 줄은 1000개까지이고 가득 차면 새 줄을 버린다 (화면은 기다리지 않는다). 서버를 끌 때는 남은 줄을 5초까지 마저 저장한다. 일꾼은 Spring의 실행기 빈으로 두지 않아 AI 분석의 일꾼(10)과 섞이지 않는다
- **언제**: 2026-11-20 JM-92 (PR #52)
- **확인**: 같은 PC에 네 판을 함께 띄우고 피드 1쪽을 500번씩 번갈아 연 결과, 사람 화면이 bot보다 늦은 정도(p50)가 main +0.27 ms, JPA 저장 +8.10 ms, INSERT 한 문장 +4.64 ms, 일꾼 스레드 저장 +0.60 ms (p95는 +0.88, +10.08, +6.87, +1.98 ms). 일꾼 스레드 판도 700줄을 순서 하나 빠짐없이 저장했다. 줄이 가득 찰 때와 끌 때는 테스트로 지킨다 (`PageFlowRecorderTest`)
- **남은 것**: 서버가 갑자기 죽으면(메모리 부족 등) 줄에 있던 몇 줄은 남지 않는다. 운영의 전후는 배포 뒤 앱 쪽 피드 p95로 본다 (기준 64 ms)
