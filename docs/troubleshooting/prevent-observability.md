# 미리 막은 문제: 문제를 빨리 알아채고 원인을 찾기

- **종류**: 미리 막은 문제 (예방). 장애가 나기 전에 "났을 때 원인을 볼 수 있게" 깔아 둔 장치와, 실제로 쓰인 곳
- **정리**: 2026-11-19. 시점은 각 장치를 처음 넣은 커밋. 기획서 11절 "문제가 생겼을 때 원인을 볼 수 있는 장치를 기능보다 먼저"

## 1. 사용자가 "에러가 났어요"라고만 하면 원인을 못 찾는 문제 → 요청마다 traceId

- **예상한 문제**: 요청이 여럿 섞인 로그에서 한 사람의 요청을 골라내기 어렵다
- **미리 한 것**: 요청마다 traceId를 만들어 그 요청의 모든 로그 줄에 붙이고(MDC), 응답 머리말 `X-Trace-Id`와 에러 응답에도 넣는다. 사용자가 번호만 알려 주면 그 요청의 로그만 볼 수 있다
- **언제**: 2026-10-29 S0 (PR #3, PR #4)

## 2. 느려졌는지 알 수 없는 문제 → 요청마다 한 줄의 기록

- **예상한 문제**: 어떤 화면이 언제부터 느려졌는지 나중에 알 수 없다
- **미리 한 것**: 요청이 끝날 때마다 `GET / -> 200 (35ms)`처럼 메서드, 경로, 상태, 걸린 시간을 한 줄 남긴다 (`TraceIdFilter`)
- **언제**: 2026-10-29 S0 (PR #3)
- **확인**: 11-04부터 CloudWatch에 8만 3천 줄이 쌓여 있었고, 2026-11-19 이것으로 화면별 p50, p95를 처음 뽑았다 (JM-91). 따로 장치를 더하지 않고도 응답 시간 기록이 이미 있었다

## 3. 서버를 다시 만들면 로그가 사라지는 문제 → JSON 로그를 CloudWatch에

- **예상한 문제**: 컨테이너 로그는 컨테이너를 새로 만들면 사라진다. 여러 줄짜리 에러는 검색하기 어렵다
- **미리 한 것**: 운영 로그를 JSON(ECS 형식) 한 줄로 찍어 CloudWatch Logs `/macros/server`로 보낸다. 배포로 컨테이너가 바뀌어도 90일 남고, traceId와 레벨로 검색한다
- **언제**: 2026-11-04 S4-6 (`d5a7451`)
- **확인**: 2026-11-19 이 로그로 앱 쪽 응답 시간과 AI 응답 시간(127건 p50 2.4초, p95 4.1초)을 뽑았다
- **더한 것**: nginx 접속 기록(글자 줄, IP 없음)도 2026-11-26부터 같은 로그 그룹의 `macros-nginx-1`로 보낸다 (JM-91, PR #61). 그 전에는 서버 안 파일이라 오래된 것부터 지워졌다 (11-26에는 11-08부터만 남아 있었다). 보내는 방식은 10번

## 4. 에러가 나도 아무도 모르는 문제 → 에러 경보 메일, 다운 알림

- **예상한 문제**: 사용자가 알려 주기 전에는 에러를 모른다. 사이트가 통째로 멈춰도 모른다
- **미리 한 것**: 로그에 ERROR가 한 번이라도 찍히면 5분 안에 메일이 온다 (지표 필터 `app-error` → 경보 → SNS). 바깥의 UptimeRobot이 5분마다 상태 검사 주소를 보고 응답이 없으면 메일을 보낸다. 장애 대응 순서는 기획서 16절에 적어 두었다
- **언제**: 2026-11-04 S4-6 (PR #6, PR #8)
- **남은 것**: 배포 때의 502는 앱 오류가 아니라 이 경보에 걸리지 않는다 → [2026-11-10-deploy-502](2026-11-10-deploy-502.md)

## 5. 음식이 아닌 사진이 올라와도 모르는 문제 → 사진 검토 경보

- **예상한 문제**: AI가 음식이 아니라고 본 사진(불쾌한 사진 등)이 피드에 그대로 남는다. 11-13 발표 중에 실제로 올라와 운영자 API로 지웠다
- **미리 한 것**: 그런 사진은 가리고, 가릴 때마다 5분 안에 메일이 온다 (지표 필터 `photo-held` → 경보). 운영자는 관리자 화면에서 보고 올리거나 지운다 (JM-80)
- **언제**: 2026-11-15 JM-80 (`70bf2fb`), 경보 11-16

## 6. AI 분석이 느려지거나 실패해도 모르는 문제 → 분석마다 기록과 운영자 통계

- **예상한 문제**: AI가 느려지거나 실패하거나 토큰을 많이 쓰기 시작해도 알 수 없다
- **미리 한 것**: 분석마다 모델, 토큰, 걸린 시간, 결과 상태를 DB와 로그에 남긴다. 운영자 통계에서 성공률, 평균과 p95 시간, 토큰 합계, 하루 한도 사용량을 본다
- **언제**: 분석 기록 2026-11-02 (S2), 운영자 통계 11-11 JM-68 (PR #28), 관리자 화면의 통계 11-17 JM-75 (PR #44)
- **확인**: 30일 152건, 성공률 100%, 평균 2,505 ms, p95 4,040 ms (11-18). 기획서 17절의 목표(p95 15초 미만) 안이다

## 7. 고친 것이 나아졌는지 말할 수 없는 문제 → 측정 기반 (JM-91)

- **예상한 문제**: 성능, 비용, 사용자 경험을 고쳐도 숫자가 없으면 나아졌는지 말할 수 없다
- **미리 한 것**: 바꾸기 전에 기준선을 남기고(비공개 기록 저장소 `before-perf.txt`), 같은 방법으로 다시 재는 스크립트(`measure_live.py`, `nginx_perf.py`)와 CloudWatch 쿼리를 남겼다. 스프린트를 닫을 때마다 그 주의 숫자를 한 줄 남긴다
- **언제**: 2026-11-18 ~ 11-19 JM-91 (PR #49)
- **확인**: 이 기준선에서 이 폴더의 찾은 문제 다섯 가지가 나왔다 ([README](README.md))

## 8. 잘못된 요청 하나로 에러 경보가 울리는 문제 → 요청이 잘못되면 400번대와 WARN (JM-107)

- **예상한 문제**: 경보(4번)는 ERROR 한 줄에 울린다. 사용자가 보낸 값이 잘못됐을 뿐인데 서버가 ERROR를 남기면, 누구나 주소 하나로 경보를 울릴 수 있고 진짜 서버 오류가 그 사이에 묻힌다
- **미리 한 것**: 요청이 잘못된 경우를 하나씩 이름으로 가려 400번대로 답한다. 서버(Tomcat)가 값을 읽지 못한 예외는 그 예외에 담긴 상태로 답하고 WARN 한 줄만 남긴다(보낸 값은 남기지 않는다). 모양이 잘못된 업로드, form 칸 이름의 대괄호와 점, 비밀번호 칸이 없는 form도 400번대나 입력 화면으로. 아주 큰 쪽 번호는 읽을 수 있는 가장 큰 쪽으로 줄이고, JSP 엔진의 미리 컴파일 신호와 PUT, PATCH, DELETE의 form 읽기는 껐고, API 오류는 Accept와 상관없이 JSON으로 보낸다. 사용자가 끊은 연결은 ERROR 없이 끝낸다. 디스크나 임시 폴더 같은 서버 쪽 문제는 그대로 ERROR다. 실제 Tomcat을 띄우는 테스트(`BrokenRequestValueTest`)가 ERROR 0줄을 지킨다
- **언제**: 2026-11-20 JM-107 (PR #52). JM-92 PR 전 검토에서 찾았다 ([2026-11-20-bad-request-values-alarm](2026-11-20-bad-request-values-alarm.md))
- **확인**: 로컬에서 잘못된 요청 69가지를 보내 5xx 40가지 → 0, ERROR 42줄 → 0줄. 고치기 전 코드에서는 새 테스트가 모두 실패했다
- **남은 것**: 새로 생기는 화면이나 값도 같은 길을 타는지는 이 테스트에 경우를 더해 지킨다. 같은 검토에서 찾았지만 고치지 않은 것은 비공개 기록에 있다

## 9. 기록하는 장치가 실패해서 화면이 깨지거나 에러 알림이 울리는 문제 → 안에서 받고 경고만

- **예상한 문제**: 방문 수나 사용자 흐름처럼 화면마다 도는 기록이 실패하면(DB가 잠깐 느림, 이상한 머리말이나 주소 값) 그 화면이 에러가 되거나, Spring이 ERROR 로그를 찍어 에러 알림 메일(4)이 쓸데없이 울린다
- **미리 한 것**: 기록은 화면을 다 그린 뒤(`afterCompletion`)에 하고, 저장하는 쪽(`VisitCounter`, `PageFlowRecorder`)과 사용자 흐름의 인터셉터 전체가 예외를 안에서 받아 경고 로그(예외 이름만)를 남기고 넘어간다. Referer처럼 아무 값이나 올 수 있는 머리말은 모양이 틀리면 없는 것으로 보고, 글자가 깨진 주소 값(Tomcat이 읽을 때 예외를 던진다)도 없는 것으로 본다. 화면을 그리다 실패한 요청은 방문 수에도 흐름에도 넣지 않는다
- **언제**: 방문 수 2026-11-18 JM-86 (PR #46), 사용자 흐름 11-20 JM-92 (PR #54)
- **확인**: JM-92를 만들 때 테스트가 실제로 잡았다. 링크 표시가 없는 화면에서 `List.of(...).contains(null)`이 예외를 던져, 인터셉터 밖으로 나가면 ERROR 로그가 찍히는 상태였다. PR 전 검토에서는 깨진 utm 값(`%ED%95`처럼 잘린 것)이 들어오면 경고만 남고 그 방문의 첫 줄을 통째로 잃는 것을 로컬 서버로 재현해 고쳤다. 지금은 저장하는 쪽이 예외를 던질 때, 주소 값이 깨졌을 때, 화면을 그리다 실패했을 때를 테스트로 지킨다 (`PageFlowInterceptorTest`, `VisitCountInterceptorTest`)

## 10. 기록을 보내는 곳이 막히면 사이트도 멈추는 문제 → nginx 기록은 non-blocking으로 (JM-91)

- **예상한 문제**: nginx 접속 기록을 CloudWatch로 보낼 때 Docker의 기본 방식(blocking)을 쓰면, CloudWatch에 닿지 않는 때에 nginx를 새로 켜면(nginx 설정이 바뀐 배포, 재부팅) 스트림을 만들지 못해 nginx가 뜨지 않는다. nginx는 app과 달리 하나뿐이라 그대로 사이트가 멈춘다. 오래 막히면 기록을 넘기지 못한 nginx가 요청 처리까지 기다릴 수도 있다
- **미리 한 것**: nginx만 `mode: non-blocking`, `max-buffer-size: 4m`으로 보낸다 (`deploy/compose.yaml`의 `x-logging-cloud-nginx`). 스트림 만들기는 뒤에서 다시 시도하고, 넘기지 못한 기록은 메모리 4 MB에 모았다가 넘치면 버린다. 기록 몇 줄을 잃더라도 사이트는 멈추지 않는다
- **언제**: 2026-11-26 JM-91 (PR #61)
- **확인**: 내 PC에서 CloudWatch에 닿지 않는 주소로 두 방식을 켜 봤다. blocking은 `failed to initialize logging driver`로 켜지지 않았고(종료 코드 125), non-blocking은 켜졌다. 서버의 Docker(25.0.18)와 같은 버전대의 소스도 같다 (non-blocking이면 스트림 만들기를 뒤에서 다시 시도한다)
- **남은 것**: app은 아직 기본값이다 → [2026-11-26-app-log-blocking](2026-11-26-app-log-blocking.md). CloudWatch가 막혔던 동안 버려진 nginx 기록은 되살릴 수 없다 (그 시간의 숫자가 빈다)
