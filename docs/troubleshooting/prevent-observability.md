# 미리 막은 문제: 문제를 빨리 알아채고 원인을 찾기

- **종류**: 미리 막은 문제 (예방). 장애가 나기 전에 "났을 때 원인을 볼 수 있게" 깔아 둔 장치와, 실제로 쓰인 곳
- **정리**: 2026-11-19. 시점은 각 장치를 처음 넣은 커밋. 기획서 11절 "문제가 생겼을 때 원인을 볼 수 있는 장치를 기능보다 먼저"

## 1. 사용자가 "에러가 났어요"라고만 하면 원인을 못 찾는 문제 → 요청마다 traceId

- **예상한 문제**: 요청이 여럿 섞인 로그에서 한 사람의 요청을 골라내기 어렵다
- **미리 한 것**: 요청마다 traceId를 만들어 그 요청의 모든 로그 줄에 붙이고(MDC), 응답 머리말 `X-Trace-Id`와 에러 응답에도 넣는다. 사용자가 번호만 알려 주면 그 요청의 로그만 볼 수 있다
- **언제**: 2026-10-29 S0 (PR #3, PR #4)

## 2. 느려졌는지 알 수 없는 문제 → 요청마다 한 줄의 기록

- **예상한 문제**: 어떤 화면이 언제부터 느려졌는지 나중에 알 수 없다
- **미리 한 것**: 요청이 끝날 때마다 `GET / -> 200 (35ms)`처럼 메서드, 경로, 상태, 걸린 시간을 한 줄 남긴다 (`TraceIdFilter`)
- **언제**: 2026-10-29 S0 (PR #3)
- **확인**: 11-04부터 CloudWatch에 8만 3천 줄이 쌓여 있었고, 2026-11-19 이것으로 화면별 p50, p95를 처음 뽑았다 (JM-91). 따로 장치를 더하지 않고도 응답 시간 기록이 이미 있었다

## 3. 서버를 다시 만들면 로그가 사라지는 문제 → JSON 로그를 CloudWatch에

- **예상한 문제**: 컨테이너 로그는 컨테이너를 새로 만들면 사라진다. 여러 줄짜리 에러는 검색하기 어렵다
- **미리 한 것**: 운영 로그를 JSON(ECS 형식) 한 줄로 찍어 CloudWatch Logs `/macros/server`로 보낸다. 배포로 컨테이너가 바뀌어도 90일 남고, traceId와 레벨로 검색한다
- **언제**: 2026-11-04 S4-6 (`d5a7451`)
- **확인**: 2026-11-19 이 로그로 앱 쪽 응답 시간과 AI 응답 시간(127건 p50 2.4초, p95 4.1초)을 뽑았다

## 4. 에러가 나도 아무도 모르는 문제 → 에러 경보 메일, 다운 알림

- **예상한 문제**: 사용자가 알려 주기 전에는 에러를 모른다. 사이트가 통째로 멈춰도 모른다
- **미리 한 것**: 로그에 ERROR가 한 번이라도 찍히면 5분 안에 메일이 온다 (지표 필터 `app-error` → 경보 → SNS). 바깥의 UptimeRobot이 5분마다 상태 검사 주소를 보고 응답이 없으면 메일을 보낸다. 장애 대응 순서는 기획서 16절에 적어 두었다
- **언제**: 2026-11-04 S4-6 (PR #6, PR #8)
- **남은 것**: 배포 때의 502는 앱 오류가 아니라 이 경보에 걸리지 않는다 → [2026-11-10-deploy-502](2026-11-10-deploy-502.md)

## 5. 음식이 아닌 사진이 올라와도 모르는 문제 → 사진 검토 경보

- **예상한 문제**: AI가 음식이 아니라고 본 사진(불쾌한 사진 등)이 피드에 그대로 남는다. 11-13 발표 중에 실제로 올라와 운영자 API로 지웠다
- **미리 한 것**: 그런 사진은 가리고, 가릴 때마다 5분 안에 메일이 온다 (지표 필터 `photo-held` → 경보). 운영자는 관리자 화면에서 보고 올리거나 지운다 (JM-80)
- **언제**: 2026-11-15 JM-80 (`70bf2fb`), 경보 11-16

## 6. AI 분석이 느려지거나 실패해도 모르는 문제 → 분석마다 기록과 운영자 통계

- **예상한 문제**: AI가 느려지거나 실패하거나 토큰을 많이 쓰기 시작해도 알 수 없다
- **미리 한 것**: 분석마다 모델, 토큰, 걸린 시간, 결과 상태를 DB와 로그에 남긴다. 운영자 통계에서 성공률, 평균과 p95 시간, 토큰 합계, 하루 한도 사용량을 본다
- **언제**: 분석 기록 2026-11-02 (S2), 운영자 통계 11-11 JM-68 (PR #28), 관리자 화면의 통계 11-17 JM-75 (PR #44)
- **확인**: 30일 152건, 성공률 100%, 평균 2,505 ms, p95 4,040 ms (11-18). 기획서 17절의 목표(p95 15초 미만) 안이다

## 7. 고친 것이 나아졌는지 말할 수 없는 문제 → 측정 기반 (JM-91)

- **예상한 문제**: 성능, 비용, 사용자 경험을 고쳐도 숫자가 없으면 나아졌는지 말할 수 없다
- **미리 한 것**: 바꾸기 전에 기준선을 남기고(비공개 기록 저장소 `before-perf.txt`), 같은 방법으로 다시 재는 스크립트(`measure_live.py`, `nginx_perf.py`)와 CloudWatch 쿼리를 남겼다. 스프린트를 닫을 때마다 그 주의 숫자를 한 줄 남긴다
- **언제**: 2026-11-18 ~ 11-19 JM-91 (PR #49)
- **확인**: 이 기준선에서 이 폴더의 찾은 문제 다섯 가지가 나왔다 ([README](README.md))
