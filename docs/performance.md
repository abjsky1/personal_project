# 성능 측정과 개선 (JM-91, 2026-11-18부터)

> 성능 개선, 비용 절감, 사용자 경험 개선을 할 때마다 **전후 숫자**로 남기려고 만든 문서다. 무엇을 어디서 재는지, 지금 숫자(기준선), 숫자를 보고 고를 개선 후보, 고친 것의 전후를 한곳에 모은다.
> - 계획과 결정 → [`PLANNING.md`](PLANNING.md) (11절 운영, 관측이 이 문서를 가리킨다)
> - 스프린트마다 한 일과 그 주의 숫자 한 줄 → [`SPRINTS.md`](SPRINTS.md)
> - 숫자의 원본(요청 하나하나의 숫자, 측정 스크립트) → 비공개 기록 저장소 `jjikmuk_update_picture`의 `update_picture/<이슈>/before-perf.txt`, `after-perf.txt`, `measure_live.py`
> - 일감 → Jira JM-91 (측정 기반), 개선은 그때마다 따로 일감

## 1. 규칙

- **바꾸기 전에 잰다.** 시작할 때 `before-perf.txt`, 배포 뒤 같은 방법으로 `after-perf.txt`를 남기고, 이 문서 8절과 SPRINTS 한 일 행에 전후를 한 줄로 적는다
- **같은 방법, 같은 조건으로 비교한다.** 같은 글 번호, 비슷한 시간대, 같은 횟수. 조건이 다르면 다르다고 적는다
- **평균만 보지 않는다.** p50(가운데)과 p95(느린 쪽 5%)를 같이 본다. 가끔 느린 요청이 사용자 경험을 망친다
- **측정 요청은 bot User-Agent로 보낸다** (`jjikmuk-perf-bot/1.0`). 조회수, 방문 수(앱의 `Visitors` 규칙), nginx 트래픽 집계에 섞이지 않는다. PowerShell의 `curl`은 Invoke-WebRequest라서 사람으로 세어지므로 쓰지 않는다
- **실제 사이트에는 읽기만 보낸다.** 글 쓰기, 댓글, AI 분석처럼 기록이 남거나 돈이 드는 요청은 시험으로 보내지 않는다. 그런 요청은 실제 사용자의 기록(CloudWatch)으로 보거나 로컬에서 잰다
- **한계도 같이 적는다.** 어디서, 언제, 몇 번 쟀는지와 무엇이 빠졌는지
- 원본 로그는 저장소에 올리지 않고 숫자만 남긴다. 로그는 CloudWatch에 90일 남는다 (처리방침의 이용 기록 3개월)

## 4. 재는 법

### 4.1 실제 요청의 응답 시간 (CloudWatch 로그 분석)

AWS 콘솔 → CloudWatch → 로그 → **로그 분석** (2026-11에 새 화면으로 바뀌었다. 예전 이름은 Logs Insights) → 로그 그룹 `/macros/server` → 기간(예: 1주) → 아래 쿼리를 붙여 넣고 **실행** (Ctrl+Enter). 새 화면은 쿼리 맨 앞에 `SOURCE "/macros/server" START=... END=... |` 줄을 스스로 붙인다. **저장한 쿼리**로 이름을 붙여 두면 다음 주에 같은 쿼리를 다시 돌린다. 요금은 읽은 로그 양만큼인데, 30일치가 30 MB쯤이라 한 번에 0.01달러도 들지 않는다. 두 쿼리 모두 2026-11-19에 실제로 돌려 3절의 숫자를 뽑았다.

화면별 응답 시간 (앱 기록 줄). 2026-11-23 무중단 배포부터는 배포 때마다 데우기 요청(화면마다 한 번, 첫 화면 2 ~ 5초)이 이 줄에 섞인다. 앱 기록 줄에는 User-Agent가 없어서 가려낼 수 없으므로, 사람이 겪는 배포 뒤 첫 요청은 nginx 기록으로 본다 (데우기는 nginx를 거치지 않고 app으로 바로 가서 nginx 기록에 없다). `head`는 주소의 첫 마디, `sub`는 숫자 없는 둘째 마디(`/posts/new`의 `/new`), `id`는 둘째 마디가 번호이면 `/`, `tail`은 번호 뒤의 마디다. 예: `GET /posts` + `id` = 글 상세, `POST /posts` + 빈 `id` = 올리기, `POST /posts` + `/confirm` = 확정:

```
filter log.logger = "backend.common.logging.TraceIdFilter"
| parse message /^(?<method>[A-Z]+) (?<path>\S+) -> (?<status>\d+) \((?<ms>\d+)ms\)$/
| filter status like /^[23]/ and path not like /^\/actuator/
| parse path /^(?<head>\/[a-z]*)/
| parse path /^\/[a-z]+(?<sub>\/[a-z]+)$/
| parse path /^\/[a-z]+(?<id>\/)\d+(?:\/|$)/
| parse path /^\/[a-z]+\/\d+(?<tail>\/[a-z]+)/
| stats count(*) as n, pct(ms, 50) as p50, pct(ms, 95) as p95, pct(ms, 99) as p99, max(ms) as worst by method, head, sub, id, tail, status
| sort n desc
| limit 40
```

LLM 응답 시간 (AI 분석, 직접 적기, 실패까지. 끝에 `, bin(1d)`를 더하면 날마다):

```
filter message like /latencyMs=/
| parse message /^(?<kind>[A-Za-z ]+):/
| parse message /status=(?<status>[A-Z_]+)/
| parse message /latencyMs=(?<ms>\d+)/
| stats count(*) as n, pct(ms, 50) as p50, pct(ms, 95) as p95, pct(ms, 99) as p99, max(ms) as worst, avg(ms) as mean by kind, status
| sort n desc
```

- 앱 기록 줄은 앱이 응답을 다 만든 시간이다 (JSP를 그리는 시간까지 들어가고, nginx와 인터넷 구간은 빠진다)
- bot 요청도 섞여 있다 (앱 로그에는 User-Agent가 없다). 사람만 보려면 4.2의 nginx 기록을 쓴다
- 컨테이너 안의 상태 검사(`/actuator/health`, 30초마다)와 업타임 모니터(HEAD)도 한 줄씩 찍힌다. 위 쿼리는 `/actuator`를 뺐다
- 사진 주소(무작위 이름)의 첫 글자가 숫자인지 글자인지에 따라 묶음이 갈리지 않게 `id`는 둘째 마디 전체가 숫자일 때만 잡는다 (11-19 첫 쿼리에서 사진이 열 줄 넘게 갈렸다)

EC2와 RDS 지표는 CloudWatch → 지표 → 모든 지표에서 EC2의 인스턴스별 지표(CPUUtilization, CPUCreditBalance, CPUSurplusCreditsCharged)와 RDS의 DB 인스턴스별 지표(CPUUtilization, FreeableMemory, DatabaseConnections, ReadLatency, WriteLatency, CPUCreditBalance, FreeStorageSpace)를 고르고, 그래프 종류를 **번호**, 옵션의 값을 **시간 범위 값**으로 두면 기간 전체의 평균, 최대, 최소가 숫자 하나씩으로 나온다 (통계는 지표마다 고른다)

### 4.2 nginx 기록 (CloudWatch, 2026-11-26부터)

2026-11-26부터 nginx 기록이 같은 로그 그룹의 `macros-nginx-1` 스트림으로 간다 (5절의 첫 조각, PR #61). 그 전 기록은 CloudWatch에 없고, 서버에 남아 있던 것을 11-26에 센 숫자가 8절에 있다. 4.1의 앱 쪽 쿼리와 경보는 JSON 칸(`log.logger`, `message`, `log.level`)으로 고르므로 nginx의 글자 줄은 섞이지 않는다. nginx 기록은(같은 날 PR #62부터 app 기록도) `mode: non-blocking`으로 보내서, CloudWatch가 오래 막히면 메모리 4 MB를 넘친 줄은 버려진다 (그 시간의 숫자가 빈다). nginx의 에러 줄(502, 413 등. nginx가 사용자 IP를 함께 적는다)은 CloudWatch로 보내지 않고 컨테이너 안 파일에만 남긴다 (`nginx/default.conf`의 `error_log`). 아래처럼 본다.

사람이 받은 응답 시간 (bot을 뺀 것, `rt`는 초 단위):

```
filter @logStream like /nginx/
| parse @message /^\S+ \S+ "(?<method>[A-Z]+) (?<path>[^ "]+)[^"]*" (?<status>\d{3}) (?<bytes>\d+) (?<rt>[\d.]+) "(?<ua>[^"]*)"/
| filter ispresent(rt) and ua not like /(?i)(bot|crawl|spider|curl|python|headless)/
| parse path /^(?<head>\/[a-z]*)(?<num>\/\d+)?(?<tail>\/[a-z]+)?/
| stats count(*) as n, pct(rt, 50) as p50, pct(rt, 95) as p95 by method, head, tail, status
| sort n desc
| limit 40
```

배포 때 502 (1분 단위):

```
filter @logStream like /nginx/
| parse @message /" (?<status>\d{3}) \d+ [\d.]+ "/
| filter status = "502"
| stats count(*) as n by bin(1m)
```

### 4.5 CPU와 메모리

- EC2: 콘솔 → EC2 → 인스턴스 `macros-server` → 모니터링: **CPU 사용률**, **CPU 크레딧 잔액**. t3.small은 평소 기준 성능(vCPU마다 20%)보다 많이 쓰면 크레딧을 꺼내 쓰는 종류라, 잔액이 줄어드는지 본다
- RDS: 콘솔 → RDS → `macros-db` → 모니터링: **CPU**, **여유 메모리**, **DB 연결 수**, 읽기와 쓰기 지연
- 서버 안 (SSH, 프롬프트가 `[ec2-user@…]$`인 창): `free -m` (메모리와 스왑), `docker stats --no-stream` (컨테이너별 CPU와 메모리, app의 한도는 1 GB), `df -h /` (디스크)
- 메모리와 디스크를 CloudWatch에 꾸준히 쌓으려면 CloudWatch 에이전트가 필요하다 (EC2 기본 지표에는 메모리가 없다) → 5절

### 첫 조각의 nginx 순서 (2026-11-26에 했다, PR #61)

1. **지금 기록을 먼저 뽑는다**: nginx 컨테이너를 새로 만들면 서버에 남은 기록(10 MB 파일 세 개)이 사라진다. 그 전에 이 기록으로 사람이 받은 응답 시간과 502를 한 번 세어 기준선에 더한다 (원본은 저장소에 올리지 않는다) → 11-18에 했다 (3절). 바꾸기 직전에 `nginx_perf.py`로 한 번 더 세면 그사이 숫자도 남는다 → 11-26 머지 직전에 한 번 더 셌다 (8절)
2. **권한을 미리 확인한다** (서버): 같은 로그 그룹으로 시험 컨테이너 하나를 보내 본다. `docker run --rm --log-driver awslogs --log-opt awslogs-region=ap-northeast-2 --log-opt awslogs-group=/macros/server --log-opt tag=awslogs-test alpine echo awslogs-test` → CloudWatch에 `awslogs-test` 스트림이 생기면 된다. 기본값(blocking)의 awslogs는 시작할 때 CloudWatch에 스트림을 만들지 못하면 컨테이너가 뜨지 않으므로, nginx를 바꾸기 전에 확인한다 → 하지 않았다. 11-23 무중단 배포 때 app1, app2가 같은 그룹에 새 스트림을 만들어 권한은 확인됐고, nginx는 non-blocking으로 보내 스트림을 만들지 못해도 먼저 뜬다 (3)
3. **`deploy/compose.yaml`을 고친다**: nginx의 `logging: *logging-local`을 `logging: *logging-cloud-nginx`로, 위의 로그 설명 주석도 맞게. 새 묶음은 app의 `x-logging-cloud`에 `mode: non-blocking`과 `max-buffer-size: 4m` 두 줄을 더한 것이다 (같은 날 PR #62에서 app도 같은 두 줄로 바꿔 묶음을 하나로 합쳤다). 기본값(blocking)이면 CloudWatch에 닿지 않을 때 nginx를 새로 켜도 뜨지 않는다 (내 PC에서 닿지 않는 주소로 재현: blocking은 `failed to initialize logging driver`로 켜지지 않고 non-blocking은 켜짐, 11-26). nginx는 app과 달리 하나뿐이라 뜨지 못하면 사이트가 멈춘다. non-blocking은 스트림 만들기를 뒤에서 다시 시도하고, 넘기지 못한 기록은 메모리 4 MB에 모았다가 넘치면 버린다. 내 PC 시험용 `compose.local.yaml`은 nginx도 파일로 덮어쓴다. 같은 PR에서 `nginx/default.conf`에 `error_log`를 더해, IP가 들어가는 에러 줄은 표준 출력(= CloudWatch)이 아니라 컨테이너 안 파일에만 error 등급으로 남긴다 (PR 전 검토에서 찾음. 내 PC에서 502와 413을 만들어 Docker 기록에 IP 든 줄 0줄, 파일에만 있는 것을 확인). 같은 로그 그룹을 쓰면 보관 기간 90일을 새로 정하지 않아도 된다 (새 그룹을 만들면 보관 기간이 "만료 없음"으로 생겨 처리방침의 3개월을 넘긴다)
4. **PR → 머지 → 자동 배포**: `deploy.sh`의 마지막 단계(`docker compose up -d --no-deps nginx certbot`, 2026-11-23 무중단 배포부터)가 nginx 설정이 바뀐 것을 보고 nginx 컨테이너를 새로 만든다 (보통 1~2초 끊긴다. 느린 사진 전송이 걸려 있으면 옛 nginx가 그 요청을 최대 10초 기다린 뒤 끊으므로 그만큼 길어진다). 사람이 적은 때에 머지한다 → 11-26에 머지했다
5. **확인**: CloudWatch에 `macros-nginx-1` 스트림, 서버의 `docker compose logs nginx`도 그대로 되는지 (Docker가 사본을 남긴다), 사이트 200. 기존 경보(`app-error`, `photo-held`)는 JSON 줄만 보므로 nginx의 글자 줄에는 걸리지 않는다. 스트림은 배포 직후 꼭 본다: non-blocking이어도 nginx가 켜질 때 스트림을 끝내 만들지 못하면(권한이 스트림 이름으로 묶였거나 CloudWatch가 하루쯤 닿지 않음), Docker 25의 awslogs는 보내지 못한 줄을 4,096줄(지금 양으로 하루쯤)까지 쥐고 기다리다가, 그 뒤 nginx를 끌 때 끝나지 않는다 (배포 7단계가 멈추고 80, 443번이 닫힌 채. moby v25.0.5의 awslogs `Log`와 `RingLogger.Close`로 확인). 서버에서 `sudo journalctl -u docker --since -30min | grep -i awslogs`에 `Error while trying to initialize awslogs`가 없으면 만들어진 것이다. 켜질 때 스트림 만들기에 성공한 컨테이너는 그 뒤 CloudWatch가 막혀도 못 보낸 줄을 버리며 비우므로 멈추지 않는다. app도 non-blocking이 된 뒤로(PR #62) 새 자리를 켜는 배포마다 같은 일이 있을 수 있어, 배포 뒤 같은 명령으로 본다 (app은 배포 때 옛 자리를 끄다 멈추면 배포 작업만 멈추지만, 사이트를 맡은 자리가 메모리 초과 등으로 꺼지면 다시 켜지지 않는다. `awslogs-create-stream: "false"`는 서버의 Docker 25가 받지 않는다)
6. **4.2의 쿼리를 저장한다** (운영자가 콘솔의 Logs Insights에서). 되돌릴 때는 3의 한 줄을 되돌리는 PR

## 7. 계속 살펴볼 것

- **DB 인덱스**: 글이 약 130개뿐이라 지금은 어떤 인덱스도 숫자 차이를 내지 않는다. 로컬에 많은 데이터를 넣고 EXPLAIN과 걸린 시간으로 비교한다 (`posts`의 상태와 번호, `comments`의 글 번호와 상태, 방문 수 표). `posts`의 사진 이름 둘(`image_key`, `thumbnail_key`)은 JM-95에서 넣었다: 따로 만든 DB의 글 10만 개에서 글 찾기 13 ~ 25 ms → 0.26 ~ 0.37 ms (8절)
- **트랜잭션**: 글 상세는 조회수 때문에 쓰기 트랜잭션이다. 올리기는 사진 처리와 S3 저장, DB 저장이 한 요청 안에 있다. AI 분석은 일꾼 2명과 줄 50으로 요청 밖에서 한다
- **스프링 코드**: 분석 두 번 읽기, JSP 그리기, DB 연결 수(Hikari 기본 10)와 RDS 연결 한도, `open-in-view`는 이미 끔
- **Redis**: 세션, 횟수 제한, 조회수 모으기, 자주 읽는 피드 캐시. 쓸 이유가 숫자로 생겼을 때 넣는다 (먼저 JM-62)
- **비용**: AI 호출 수와 토큰, CloudWatch 로그 양, S3 저장과 내보내기
